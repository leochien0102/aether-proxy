## 2. init 代码复审

逐项核对卡片“冻结行为”1–6，均成立：

- **错误暂存/消费**：`stop_service` 进入即把 `_AETHER_PROXY_STOP_HOOK_RC=0`，两处已检查失败置 1；`service_stopped` 先取走再清零，独立 callback 与下一次 stop 不会继承旧错误（I3 reset 场景已证）。
- **优先级**：cleanup 非 0 时精确保留其原 rc（3/37 逐值相等），只有 cleanup 成功才采用 hook 错误；`stop` 的最终 rc 经 rc.common 的 `if … service_stopped` 原样返回。
- **不阻止 kill**：hook 失败仍执行 `procd_kill` 与 `service_stopped`，事件顺序断言 `lock, kill, cleanup, open-service, trigger, close-service` 完整；没有用 `return` 假装能阻止。
- **禁用分支**：`reload_service` enabled=0 捕获 stop rc，仍清 manual-stop 标记；stop/cleanup 非 0 优先，否则 mark 删除失败返回 1；无实例+intent 仍收口，无实例+无 intent 仍是 no-op（I4 八组覆盖）。
- **TERM 范围**：两分支都只在 `stop` 前 `trap '' TERM`、stop 返回后先 `trap - TERM` 再决定返回失败或 start；enabled=1 分支在写 intent 之后才屏蔽（准备 intent 阶段不扩大）；普通 stop 不新增屏蔽（I5 用真实子 shell 的 SIGTERM 与持有 PID 证明，不是查 trap 文本）。
- **正常路径不变**：文件操作正常时 hook rc=0，`stop` 仍返回 cleanup rc；`printf ''` 与 `:` 一样只创建/截断空标记文件。因此 opkg prerm 的 `stop` 在正常升级下仍返回 0（设备 `default_prerm` 本身也不采用 stop 返回值，我另行只读核对过），不存在“升级因新 rc 被中止”的风险。
- **未扩大保护**：没有新增状态文件/RPC/配置/保护入口；opkg 普通 stop/start、无 intent 的 procd respawn、首次接管仍不受 intent 保护；`service_stopped` 的 `stop` 语义、cleanup、trigger 重新登记均保持。

两处非阻断备注：

1. `restart()` 里的 `umask 077` 仍在该函数内全局生效（T15.1 遗留），本卡未触碰；对后续 `start` 无文件创建，实际无影响。
2. `trap - TERM` 恢复的是默认处理而非调用者自定义 trap；卡片明确不承诺保存任意原 trap，且与固件 rc.common 的 restart 一致。
