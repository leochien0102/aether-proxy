# M14 任务卡：raw-log collector 存活修复

> **项目与范围**：本文件的任务卡全部属于 **aether-proxy** 仓库（主检出 `/workspace/openwrt/aether-proxy`，GitHub `leochien0102/aether-proxy`）。
> 执行时只在 `tests/start-task.sh <卡号>` 或本卡指定 worktree 中读写；
> **不准修改主检出，也不准碰 `/workspace/openwrt` 下的任何其他仓库**（helloworld、luci-extras、openwrt-actions 等，含其构建目录）。
> 任务卡要求「参考」其他仓库的文件时，只读不写。执行约定见 [README.md](README.md)「执行约定」。

背景（2026-11-05，r3 实测）：T13.2 的 collector 启动后只写入启动批次，随后退出：

```text
CHILD_CRASHED [name=raw-log code=1 restart_in=null]
```

`supervise` 对 raw-log 采用“失败只 warn、不重启”的策略，导致 raw.log 停更；x86 只有 2 行、H28K 52 行，均远少于 logread 历史。需要让 collector 在 logread 结束/失败后自动恢复，同时保留现有 tmpfs/0600/轮转和“系统 logd 不动”的边界。

---

## T14.1 raw-log collector 自动续跑

- **分支**：`fix/rawlog-loop`，基于 `b57a4dd`（0.6.3-r3）。
- **允许改动**：`aether-proxy/files/aether-proxy-rawlog.sh`、`aether-proxy/src/lib/supervise.uc`（如需）、`aether-proxy/src/lib/daemon.uc`（如需）、tests、docs/09、报告。不改 UI/API/配置/版本。
- **要求**：
  1. `logread -f` 或 awk 正常 EOF/失败退出后，collector **自动重启采集**；不得只 warn 一次后永久停更。
  2. 用有限退避避免 logread 立即失败时忙循环（例如 1–5 秒；连续失败仍保持有界）。
  3. TERM/INT 停止时干净退出、回收 logread/awk、删除 FIFO；不能因为自动重启导致服务停止时残留进程。
  4. 保留 `/var/run/aether-proxy/raw.log`、`raw.log.1`、0600、1 MiB/2000 行轮转；不写 flash，不清/改系统 logd。
  5. 不重复写同一批日志：重启 logread 只取新行（`-f` 无 `--lines` 历史），必要时记录一次 info/warn 说明采集重启。
  6. 启动后应能持续捕获 `SERVICE_STARTED`、`PROXY_HEALTHY` 等后续事件，而不是只有启动瞬间。
- **测试**：
  - fake logread 正常退出后 collector 自动重启并捕获下一批行；
  - fake logread 连续失败时不忙循环、有退避；
  - TERM 时不重启、子进程/FIFO 全回收；
  - 轮转/权限/上限回归；
  - 真实 H28K 或 x86：重启服务后 `raw.log` 持续增加，`ps` 有 raw-log，日志不再 `CHILD_CRASHED` 后停更。
- **验收**：collector 持续存活；系统日志不变；不 bump、不 push。

## T14.2 切页时红色横幅：uci.load 失败被缓存

- **工作区**：`/workspace/openwrt/aether-proxy-wt/T14.2`（已就绪，含本卡）；**分支**：`fix/t14.2-uci-load-retry`，基于 `7d93f87`（0.6.3-r4）。
- **允许改动**：`luci-app-aether-proxy/htdocs/luci-static/resources/aether-proxy/common.js`（新增读配置帮助函数）、6 个视图的 `load()` 调用点、对应 LuCI 测试、报告。不改 RPC 语义、不改 `rpc.js`/`luci.js`、不 bump 版本。
- **现场证据（2026-11-06，浏览器 Console）**：
  `Uncaught (in promise) Error: No related RPC reply`；
  栈：`flushRequestQueue ← Request.request ← rpc.call ← uci.load ← view.load ← overview.refreshConfig`。
- **根因（三步）**：
  1. LuCI 批量层（`luci.js` 的 `flushRequestQueue`）在响应不是「与批次一一对应的 JSON 数组」时，用 `new Error('No related RPC reply')` 拒绝整批请求；偶发一次。
  2. `uci.load()` 把**失败的 Promise 缓存在 `uci.loaded[config]`**（`uci.js` 的 `loadPackage`），之后所有 `uci.load('aetherproxy')` 直接复用这个 rejected promise，**不再发请求**。
  3. 视图 `load()` 失败 → `View` 构造链的 `.catch(L.error)` → 红色横幅；文档不重载就一直复现，整页刷新才自愈。
  （`max_requests 3` 超限只是排队，不是本次错误来源；`hashchange` 在主题 SPA 路由下不会触发。）
- **外部触发（2026-11-06 实机证据）**：`ubus subscribe service` 捕获到
  `instance.respawn {service:"uhttpd", pid:10993, exit_code:139, respawn_count:4}`（139 = SIGSEGV）；
  4 个并发 POST 到 `/cgi-bin/luci/admin/ubus` 即可复现，uhttpd 崩溃后被 procd 秒级拉起。
  设备为 `uhttpd 2025-10-03-ebb92e6b-1`（`-n 3`），不含上游 master 2026-09/11 的 script-slot 与缓冲边界修复
  （`8e0d492c`、`8791d398`、`b0aaa81a`）。因此**本卡只能让 app 从崩溃中恢复，不能阻止 uhttpd 崩溃**；
  根治需要换 uhttpd/固件，另案处理，不在本卡调 `max_requests`。
- **要求**：
  1. 公共模块新增 `load_config()`：`uci.load('aetherproxy')` 失败 → `uci.unload('aetherproxy')` → 重试一次；再失败原样抛出（不吞错、不掩盖持续故障）。
  2. 6 个视图的 `load()` 改用它；保存/应用路径不动。
  3. 重试只针对初次读配置；不留定时器、不影响 `ap.poll`。
- **测试**：
  - 第一次 reject、第二次 resolve：最终成功，且中间调用过 `uci.unload`；
  - 连续两次 reject：只重试一次，错误继续上抛；
  - 首次成功：不 unload、不重复请求；
  - 两个视图并发调用时不会无限重试。
  - `tests/luci/run.sh` 全绿；变异 ≥3（去掉 unload / 去掉重试 / 改成重试两次）。
- **验收**：H28K 上用 DevTools 把 `/ubus` 请求 Block 一次制造失败——现状出红横幅，修复后自动重试成功、横幅不出现；持续失败仍能看到横幅。不 bump、不 push。
- **另记（另卡）**：主题 SPA 路由下旧页 `ap.poll` 不停，会放大 RPC 抖动；单独一张小卡，本卡不改 poll 生命周期。
