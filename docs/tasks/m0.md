## T0.1 仓库骨架与包

- **必读**：[01](../01-architecture.md)「包拆分」「仓库布局」、[12](../12-ucode.md) 全文、[05](../05-config.md)「默认配置文件」
- **产出**
  - `aether-proxy/Makefile`、`luci-app-aether-proxy/Makefile`
  - `aether-proxy/src/aether-proxy`：入口。支持 `--help`、`version`（输出 `aether-proxy <PKG_VERSION>`，版本号在构建时写入 `const.uc`），未知子命令输出用法并以退出码 2 退出
  - `aether-proxy/src/lib/const.uc`：[01](../01-architecture.md) 常量表中的全部常量
  - `aether-proxy/src/lib/sys.uc`：`run(argv, opts)`、`q(arg)`、`write_atomic(path, content)`（规格见 [12](../12-ucode.md)「编码规则」）
  - `aether-proxy/src/lib/log.uc`：`event(level, code, args, message)`，按 [09](../09-logging.md) 的格式写 syslog（用 `log` 模块）。本卡**不写** events.jsonl
  - `aether-proxy/files/aether-proxy.config`（内容即 05 中的默认配置）、`files/30-aether-proxy.nft`（内容见 [02](../02-dataplane.md)「与 fw4 的对接」）
  - `luci-app-aether-proxy`：菜单 JSON、ACL JSON、一个只显示 `aether-proxy version` 输出的占位视图，以及最小的 rpcd ucode 插件（只实现 `status` 方法，返回 `{"version": "..."}`）、`po/zh_Hans/aether-proxy.po`
  - 本卡**不包含** init 脚本、hotplug（属于 M2）
- **不准**：实现任何业务逻辑；在 `sys.uc` 以外调用 `system()` / `fs.popen()`
- **验收**
  1. 在 OpenWrt 构建树中执行 `make package/aether-proxy/compile package/luci-app-aether-proxy/compile V=s`，两个包都能生成
  2. 安装到 24.10 虚拟机：`aether-proxy version` 输出版本号；`aether-proxy foo; echo $?` 输出 `2`
  3. `ls /usr/share/nftables.d/chain-pre/input/30-aether-proxy.nft` 文件存在，并且 `fw4 reload` 没有报错
  4. LuCI 菜单「服务 → aether-proxy」能打开占位页面，并显示版本号
  5. `grep -rn "system(\|popen(" aether-proxy/src/lib | grep -v sys.uc` 没有输出

## S1 子进程日志转发（探针）

- **问题**：`uloop.process` 不能重定向子进程的 stdio。要在 daemon 中监督 Xray 和 chinadns-ng，并把它们的输出分别以
  `aether-proxy-xray`、`aether-proxy-dns` 标签写入 logd（[09](../09-logging.md)「子进程日志」中的三个候选方案）。
- **做法**：在 24.10.8 虚拟机上为每个方案写一个原型脚本（`spikes/S1/`），子进程用一个会持续输出、并能被信号终止的 shell 脚本模拟。
- **必须回答**
  1. 每个方案能否得到正确的 pid；SIGTERM 能否结束子进程且不留下孤儿进程
  2. 子进程退出时能否拿到退出码，延迟多久
  3. 子进程高速输出（每秒 1000 行）时 daemon 是否阻塞或丢行
  4. daemon 被 `kill -9` 后，子进程是否残留（预期会残留，由 cleanup 处理；记录实际情况）
- **产出**：修改 [09](../09-logging.md)「子进程日志」，写明选定的方案和理由；如果影响 [04](../04-lifecycle.md) 的进程模型，一并修改。

## S2 nft 规则在真机上的行为（探针）

- **做法**：按 [02](../02-dataplane.md) 的模板手写一份完整的规则文件（`spikes/S2/aether-proxy.nft`：`lan_ifaces=br-lan`，`gfw` 模式，开启 `dns_hijack` 和 `quic_block`，
  每个主机集合填一个示例元素），分别在 24.10.8 与 25.12.5 虚拟机上加载。
- **必须回答**
  1. `nft -c -f` 与 `nft -f` 是否都通过；同一文件连续加载两次（整表替换）是否通过，过程中计数器是否表明有包未经规则处理
  2. `fw4 reload`、`fw4 restart` 之后 `inet aetherproxy` 是否还在
  3. `ether saddr` 在 `br-lan` 的 prerouting 中能否匹配到 LAN 客户端
  4. forward 链中的 `reject` 对 UDP 443 是否生效（客户端收到 ICMP port-unreachable）
  5. 用 `nft -j list set` 导出、渲染进新文件后再加载，动态集合元素能否原样恢复
- **产出**：在 02 中记录结论；模板需要修改的，直接修改。

## S3 透明代理端到端（探针）

- **做法**：在 24.10.8 虚拟机上手工部署：按 [06](../06-nodes-subscription.md) 的模板写好 `xray.json`（指向测试节点），加上 S2 的规则文件和 ip rule / route，
  在虚拟机后面挂一个 LAN 客户端。
- **必须回答**
  1. 客户端的 TCP 流量经过节点（节点侧能看到连接）；直连目标确实不经过节点
  2. 游戏模式主机的 UDP 经过节点（例如在客户端上做一次 DNS-over-UDP 查询并发往境外服务器，在节点侧观察）
  3. Xray 监听 `0.0.0.0` 时，从 LAN 直接连接 31080 端口被 `input_guard` 丢弃
  4. 经 HTTP 入站 `127.0.0.1:31081` 访问 `probe.url` 能得到 204
  5. 经 `127.0.0.1:31082` 的 TCP DNS 查询经过节点
- **产出**：在 02、06 中记录结论，修正模板。

## S4 chinadns-ng 配置（探针）

- **做法**：在 S3 的环境中，用 [03](../03-dns.md) 的模板渲染 `gfw`、`bypass_cn` 两种模式以及 T1、T2 两个级别的配置并逐一运行。
- **必须回答**
  1. 配置能否被接受（包括空的 `group-dnl` 文件）
  2. `gfw` 模式下解析 gfwlist 中的域名后，IP 是否出现在 `inet aetherproxy gfw4` 集合中
  3. `udirect` / `uproxy` 组的结果是否进入对应集合，组的优先级是否与「后声明者优先」一致
  4. `no-ipv6` 后 AAAA 查询是否返回 NODATA；`filter-qtype 65` 是否生效
  5. 重启 chinadns-ng 后缓存确实被清空（第一次查询的耗时明显变长）
- **产出**：在 03 中记录结论，修正模板。

## S6 dnsmasq 对接（探针）

- **必须回答**（24.10.8 与 25.12.5 各测一次）
  1. 默认实例生成的配置文件路径，以及 `conf-dir=` 行的实际值
  2. 在 conf-dir 中放入只含 `no-resolv` 和 `server=127.0.0.1#31053` 的片段并重启 dnsmasq 后：上游是否只剩 31053（UCI 中 `noresolv` 为 0 时也一样）
  3. 删除片段并重启后，是否完全回到原来的上游
  4. `kill -HUP` 是否清空 dnsmasq 缓存
- **产出**：在 03「dnsmasq 对接」中写明路径规则和结论。
