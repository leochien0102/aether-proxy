## T7.1 `tools/channel/`：生成发布目录与清单

- **分支**：`m7/channel-builder`
- **必读**：[08](../08-updates.md)「范围」「发布通道」「数据格式与来源」「`manifest.json`」「签名」「发布仓库」；现有 `tools/data/build.py`（数据由它生成，本卡只调用）与 `tools/data/test_build.py`（测试写法参考）
- **允许改动**：新增 `tools/channel/`（Python 3，只用标准库）及其测试 `tools/channel/test_*.py` 与夹具 `tools/channel/fixtures/`；`.github/workflows/test.yml` 增加一步运行这些测试。不准改 `tools/data/` 的行为
- **要求**
  - `tools/channel/build.py --out <目录> --packages <编译产物目录> [--data <已生成的数据目录>] [--previous <旧 manifest.json>]`：
    1. 软件包：扫描 `--packages` 下的 `*.ipk`、`*.apk`，从文件名解析包名、版本、架构（ipk：`<名>_<版本>_<架构>.ipk`；apk：`<名>-<版本>_<架构>.apk`，架构无关的包为 `all`）。只收录 `xray-core`、`aether-proxy`、`luci-app-aether-proxy`，其他包忽略并在输出中列出。
       复制到 `--out`，清单中记 `url`（文件名）、`sha256`、`size`。同一包同一版本必须在每个出现的架构上都同时有 ipk 与 apk，缺任何一个 → 失败退出
    2. `current`/`previous`：包版本与 `--previous` 清单中的 `current` 不同 → 旧的 `current` 成为新的 `previous`（其资产文件名原样保留在清单里，发布 workflow 负责让这些文件仍在 Release 中）；相同 → 两者都沿用
    3. 数据：`--data` 目录中的五个文件逐个 gzip 为 `<名称>-<内容 sha256 前 12 位>.txt.gz`，记 `version`（同前缀）、`sha256`（解压后内容）、`size`、`lines`；不给 `--data` 时沿用 `--previous` 的 `data` 段
    4. 写 `manifest.json`（`schema: 2`，键排序、两空格缩进，`generated` 用 UTC ISO 8601）；与 `--previous` 相比除 `generated` 外全同 → 在 `--out` 写 `unchanged` 标记文件
  - `tools/channel/sign.sh <manifest.json> <私钥文件> [<公钥文件>]`：`usign -S` 生成 `manifest.json.sig`；给了公钥就再 `usign -V` 自检。**私钥只从文件读取，不打印、不写日志**
- **测试**（`python3 -m unittest discover tools/channel`，离线）：夹具包目录生成完整清单且字段齐全；缺某架构的 apk → 失败；`previous` 轮转（新版本 / 同版本两种）；只给包不给数据时沿用旧数据段；与上一份清单相同 → `unchanged`；
  签名往返：用 `tests/host/prefix/bin/usign -G` 临时生成密钥对，`sign.sh` 签名后验签通过、改一个字节后验签失败
- **验收**：`tests/review.sh` 的 FAIL 为 0；`python3 -m unittest discover tools/channel` 全过；`tools/data/test_build.py` 仍全过。

- **分支**：`m7/update-check`

- **允许改动**：新增 `lib/update.uc`、`lib/cmd/update.uc`，在入口分发 `update`（本卡只实现 `update check`；`update package`/`data` 返回 `USAGE`「尚未实现」）；`lib/cmd/status.uc` 让 `updates_available` 读 `updates.json`；
  `lib/job.uc` 增加作业种类 `update_check`；`lib/const.uc` 末尾追加 T7.3 区块；新增 `tests/update/run.sh` 与夹具、`tests/stubs/update-bin/`（`opkg`、`apk` 替身）；`aether-proxy/Makefile` 安装 `files/keys/`（目录可以为空，公钥由 T7.2 加入）
- **要求**
  - 下载：按 `channel_urls` 顺序；Xray 在运行（`state.json` 为 running/degraded 且 HTTP 端口监听）时先经 `-x http://127.0.0.1:31081` 再直连；`curl --fail --silent --show-error --max-time 30 --max-filesize <清单 1MB / 资产按清单 size>`，经 `sys.run`（超时 35 秒）；
    下载目录 `/tmp/aether-proxy-dl/`（受 `--sys-root` 前缀影响），用完删除
  - 验签：`usign -V -q -m manifest.json -P <keys 目录>`（`/etc/aether-proxy/keys/`，受 `--sys-root` 影响；`usign` 经 `--bin-dir` 可替换）；失败 → 记 `MANIFEST_BAD_SIGNATURE` 并换下一个地址；全部失败 → 退出码 4
  - 清单 JSON 解析失败或 `schema != 2` → 视同验签失败，换下一个地址
  - 资产下载函数（本卡实现与测试，T7.4/T7.5 使用）：`/tmp` 空间预检（不足 → `NO_SPACE` 不下载）、下载后校验 `size` 与 `sha256`，不符 → 删除并换下一个地址
  - 架构：读 `/etc/openwrt_release` 的 `DISTRIB_ARCH`（受 `--sys-root` 影响）；包管理器：有 `apk` 用 apk，否则 opkg（经 `--bin-dir` 可替换）
  - 已装版本：`opkg status <包>` 的 `Version:` 行或 `apk list -I <包>`；版本比较按 08「检查」
  - 写 `updates.json`（08「检查」的格式，`sys.write_atomic`），`--json` 时输出同样内容
- **测试**（`tests/update/run.sh`，不访问外网）：测试中用 `python3 -m http.server` 在随机端口起两个本地「通道」目录；用宿主机 usign 临时生成密钥对签名；真实 curl，`opkg`/`apk` 用替身。场景至少包括：
  1. 正常（opkg）：验签通过，`updates.json` 的版本、`newer`、`arch`、`pm` 正确；`status --json` 的 `updates_available` 等于它
  2. 正常（apk）：替身环境中存在 `apk` 时取 apk 的版本与资产键
  3. 第一个地址的清单被篡改 → 记 `MANIFEST_BAD_SIGNATURE`，从第二个地址取到
  4. 所有地址都篡改 → 退出码 4，不写 `updates.json`
  5. 签名密钥不在 keys 目录（换了一把私钥签名）→ 视同验签失败
  6. 清单不是 JSON / `schema` 为 1 → 换下一个地址
  7. `DISTRIB_ARCH` 不在某包的 `assets` 中 → 该包 `newer: false`、记 `ARCH_UNSUPPORTED`
  8. 包未安装 → `installed: null`；版本比较 `26.10.10-r1 > 26.9.30-r5`、`26.9.30-r6 > 26.9.30-r5`
  9. 资产下载函数：sha256 不符 → 删除并失败；`/tmp` 空间不足（测试钩子让可用空间读数变小，做法自选，不准新增命令行选项）→ `NO_SPACE`
  10. `job start update check` 能跑完并得到同样的结果
- **验收**：`tests/review.sh` 的 FAIL 为 0；`tests/update/run.sh` 全过；`tests/job/run.sh`、`tests/cli/run.sh` 仍全过。

    opkg：`opkg install <文件>`（`--previous` 与回滚时加 `--force-downgrade`）；apk：`apk add --allow-untrusted <文件>`（仅在验签与哈希都通过之后）→ 安装后检查 → 失败则安装清单中的 `previous` 资产回滚

  - daemon 的 SIGUSR2：停止 Xray 子进程并按当前 `current/xray.json` 重新拉起（经 supervise，退避计数归零），随后立即执行一轮 monitor；启动失败的退避期间与 `failsafe` 状态下忽略
  - 结果（`--json`）：`{ "ok", "package", "from": <旧版本>, "to": <新版本>, "rolled_back": bool, "code" }`；成功记 `UPDATE_INSTALLED`，回滚记 `UPDATE_ROLLED_BACK`
- **测试**：扩展 `tests/update/run.sh`（沿用 T7.3 的本地通道与临时密钥；`opkg`/`apk` 替身记录调用参数、可控退出码与安装后的版本；init 脚本替身记录 `restart`；用一个后台写入 `state.json` 的辅助模拟 daemon 的检测结果）。场景至少包括：

  2. apk 安装：调用 `apk add --allow-untrusted <资产>`
  3. 资产 sha256 不符：**没有调用**包管理器
  4. 本机架构没有该包的资产 → `ARCH_UNSUPPORTED`，没有下载
  5. 安装后检查失败 → 安装了 `previous` 资产（opkg 带 `--force-downgrade`）、记 `UPDATE_ROLLED_BACK`、`rolled_back: true`
  6. 检查失败且 `previous` 为 `null` → 不回滚、`UPDATE_VERIFY_FAILED`
  7. `--previous`：直接安装 `previous` 资产（带 `--force-downgrade`）
  8. `aether-proxy` 更新：调用了 init 脚本的 `restart`，`state` 进入 `running` 后成功
  9. 未知包名 → `USAGE`；`job start update package xray-core` 能跑完；`update check` 作业运行中再发起 `update package` → 退出码 3（共用更新锁）

## T7.5 `update data`：规则数据更新

- **分支**：`m7/update-data`
- **必读**：[08](../08-updates.md)「数据格式与来源」「`manifest.json`」（数据项的 `sha256`/`size` 描述 .gz、`content_sha256` 描述解压后内容）「设备端流程 · 下载」「数据更新」；
  [05](../05-config.md)「列表文件的解析规则」；[04](../04-lifecycle.md)「重载」（数据变化经 reload 生效）；[09](../09-logging.md) `DATA_UPDATED`、`UPDATE_VERIFY_FAILED`；现有 `lib/update.uc`（T7.3）、`lib/data.uc`（`parse_domains`、`parse_cidrs`）、`lib/job.uc`
- **允许改动**：`lib/update.uc`、`lib/cmd/update.uc`（实现 `update data`）、`lib/job.uc`（作业种类 `update_data`）、`lib/const.uc` 末尾追加 T7.5 区块；扩展 `tests/update/run.sh` 与夹具
- **要求**
  - 对清单中的每个数据项：本机内容哈希 = `/etc/aether-proxy/data/<名称>.sha256`（存在时），否则为包内基线 `/usr/share/aether-proxy/data/<名称>.txt` 的 sha256；与清单 `content_sha256` 相同 → 跳过
  - 变化的项：`download_asset`（校验 .gz 的 `size`/`sha256`）→ 经 `sys.run` 调 `gunzip -c` 解压到 `/tmp/aether-proxy-dl/` → 解压后内容的 sha256 必须等于 `content_sha256` →
    行数 ≥ 清单 `lines` 的 90% → 每一行都符合 05「列表文件的解析规则」（域名类用 `data.parse_domains`、CIDR 类用 `data.parse_cidrs`，有任何非法行就拒绝）→
    写 `/etc/aether-proxy/data/<名称>.txt.tmp` 再 `mv`，同时写 `<名称>.sha256`（`sys.write_atomic`）。任一步失败：该项记 `UPDATE_VERIFY_FAILED { item }`、保留旧数据，**其他项照常处理**
  - 有任何一项写入成功且服务在运行（`state` 为 `starting`/`running`/`degraded`）→ 执行一次 `/etc/init.d/aether-proxy reload`；记 `DATA_UPDATED { items: [...] }`
  - 结果（`--json`）：`{ "ok", "updated": [...], "unchanged": [...], "failed": { <名称>: <原因> } }`；任一项失败时 `ok: false`、退出码 1
  - 只在内容变化时写 flash（08「数据更新」最后一段）
- **测试**：扩展 `tests/update/run.sh`（本地通道里放用 gzip 生成的数据资产，清单字段按 T7.1 的格式）。场景至少包括：
