## T9.5 节点解析重试、LKG 按节点保存、重载保留组件版本（M10 回归发现，backlog B13）

背景（2026-10-20，H28K，M10 回归窗口）：仓库所有者切换节点时「选了另一个节点、应用后仍显示原节点，重复几次才切过去」。
事件里是 `NODE_RESOLVE_FAILED`（`lkg_ip` 为空）：reload 解析新节点域名只试一次，`boot` 组走的直连境外 DNS 在这个网络里时好时坏；
而 LKG 只存最后一个节点，新节点没有兜底。同一窗口还发现重载后 `state.json` 的组件版本丢失。

  [07](../07-probe.md)；[backlog](../backlog.md) B13；`lib/apply.uc`（`resolve_node`、`read_lkg`）、`lib/probe.uc`（`resolve_node` 与检测作业）、`lib/reload.uc`（`apply_plan` 写 `state.json` 的部分）、
  `lib/monitor.uc`（`update_node_ip`）、`lib/cmd/components.uc`（`read_component_version`）；`tests/unit/apply.uc`、`tests/stubs/bin/resolveip` 与 `common.sh`、`tests/daemon/run.sh`、`tests/reload/run.sh`、`tests/probe/run.sh`；[README](README.md)「3a. 代码风格」
- **允许改动**：`lib/apply.uc`、`lib/probe.uc`、`lib/reload.uc`、`lib/const.uc`（新增常量）；上述测试与替身（替身只增加能力，不改已有行为）
- **要求**：
  1. `apply.resolve_node`：`resolveip -4 -t 3`，失败（退出码非 0，或输出中没有合法 IPv4）就重试，最多 3 次，第一次成功即停；重试之间不等待。次数与超时进 `const.uc`。
     日志与事件语义不变：只在全部失败后才走 LKG / `NODE_RESOLVE_FAILED`，中间的失败不记事件。
  2. LKG 按 03 的新格式：读取兼容旧格式；单条 IP 不合法只忽略那一条；写入只在该地址的 IP 变化时发生，写入时把该地址移到最后，超过 64 条删最前面的；读写抽成 `apply.uc` 中的函数，`resolve_node` 与检测作业共用。
  3. 检测作业（`probe nodes`）解析成功的节点地址写入 LKG：一次作业汇总后最多写一次文件，没有变化不写。检测本身的解析**不**重试（它测的是当下的可达性），也不读 LKG。
  4. 重载写回 `state.json` 时按 04 保留组件版本：路径没变沿用原 `version`，变了重新取（用 `cmd/components.uc` 的 `read_component_version`）。
- **测试**。场景至少包括：
  1. `resolveip` 替身前两次失败、第三次成功 → 解析成功，替身恰好被调用 3 次，参数含 `-t 3`，不记 `NODE_RESOLVE_*`
  2. 三次都失败、LKG 有该地址 → 用 LKG，记一次 `NODE_RESOLVE_FALLBACK`；三次都失败、LKG 没有该地址（但有别的地址）→ `NODE_RESOLVE_FAILED`
  3. 第一次就成功 → 只调用 1 次
  4. LKG：旧格式文件可读；先后成功解析 A、B 两个地址后两条都在；A 的 IP 不变时文件不重写（mtime 或写入计数）；写满 65 个地址后最早的那个被删、最新的在最后；
     文件损坏 → 视同空、不记事件，下一次成功解析写出新格式；某一条 IP 不合法 → 只忽略那一条
  5. 端到端（`tests/reload` 或 `tests/daemon` 的现有框架）：运行中切换到从未解析过的节点，`resolveip` 第一次失败第二次成功 → 重载成功，`state.json` 的 `node_id` 变为新节点；
     随后切回原节点时 `resolveip` 全部失败 → 用原节点在 LKG 中的地址成功切回（旧实现在这一步会失败）
  6. 检测作业：两个域名节点解析成功 → LKG 中有这两条，文件只写一次；再跑一次结果相同 → 不写；解析失败的节点不写
  7. 重载后 `state.json` 的 `components` 仍有 `version`（路径未变时与重载前相同）；改了 `xray_bin` 到另一个可执行替身 → 版本按新二进制重新取
  8. 原有 `tests/run.uc`、全部 `tests/*/run.sh` 照旧通过（`resolveip` 被多处使用）

是否继续提速要先知道每一段具体花在哪（读规则数据？渲染？写 staging 算哈希？`xray run -test`？重启 Xray 等监听？），所以先把计时拆细，下个窗口实测后再定。

- **分支**：`m9/reload-timing-detail`
- **必读**：[04](../04-lifecycle.md)「重载」最后关于 `steps` 与「细分」的两段（2026-10-21 加，本卡的依据）；`lib/reload.uc`（`run`、`validate`、`validate_nft`、`apply_plan`、`execute_action`）、`lib/pipeline.uc`（`read`、`render`）；`tests/reload/run.sh`、`tests/reload/assert-event.py`；[README](README.md)「3a. 代码风格」
- **允许改动**：`lib/reload.uc`；上述测试
- **要求**：
  1. `RELOAD_APPLIED.steps` 原有五个键与含义不变；另加 `steps.detail`，键按 04「细分」。没有发生的步骤不出现（例如只改模式时没有 `xray_test`、没有 `restart_xray`）。
  2. 计时用现有的 `monotonic_ms`，不额外调用外部命令；不改变重载的任何行为、顺序与事件。
  3. `detail` 中各项之和不要求等于对应的大步骤（中间还有零碎开销），但每一项都 ≤ 它所属的大步骤。
- **测试**。场景至少包括：
  1. 切换节点：`detail` 含 `read`、`render`、`stage`、`precheck`、`nft_check`、`xray_test`、`sets_export`、`nft_render`、`nft_replace`、`restart_xray`，都是非负整数；各项 ≤ 所属大步骤（`read`+`render`+`stage` ≤ `config_render`，`precheck`+`nft_check`+`xray_test` ≤ `validate`，`sets_export`+`nft_render` ≤ `sets_export_render`，各动作之和 ≤ `actions`）
  2. 只改模式：没有 `xray_test` 与 `restart_xray`；有 `restart_chinadns`（按实际动作）
  3. 原有五个键与 T9.8/T9.9 的断言照旧通过；日志页模板不受影响（`tests/luci` 照旧通过）
  4. 报告列出宿主机上两种重载的完整 `steps`（含 `detail`）
  5. 原有 `tests/run.uc`、全部 `tests/*/run.sh` 照旧通过
- **验收**：`tests/review.sh` 的 FAIL 为 0；`tests/host/ucode tests/run.uc` 与**全部** `tests/*/run.sh` 全过（不要只跑相关套件）；报告含「场景对照」；代码符合「3a. 代码风格」与 12。
