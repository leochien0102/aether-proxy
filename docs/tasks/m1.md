# M1 任务卡：配置读取、校验、渲染器

> **项目与范围**：本文件的任务卡全部属于 **aether-proxy** 仓库（主检出 `/workspace/openwrt/aether-proxy`，GitHub `leochien0102/aether-proxy`）。
> 执行时只在 `tests/start-task.sh <卡号>` 创建的 worktree（`/workspace/openwrt/aether-proxy-wt/<卡号>`）中读写；
> **不准修改主检出，也不准碰 `/workspace/openwrt` 下的任何其他仓库**（helloworld、luci-extras、openwrt-actions 等，含其构建目录）。
> 任务卡要求「参考」其他仓库的文件时，只读不写。执行约定见 [README.md](README.md)「执行约定」。

全部是纯函数加 golden 测试，**不需要测试机**。依赖 M0 的 T0.1（骨架）和 T0.2（测试运行器）。

依赖关系：T1.1 → T1.2 → T1.3–T1.6（这四张可以并行）→ T1.7 → T1.8。

夹具命名约定：`tests/fixtures/<卡号>-<描述>/`，例如 `t13-gfw-hosts/`。每张卡只新增自己的夹具，不修改别人的期望输出；
确实需要修改时，在 PR 描述中说明原因。

## T1.1 schema 与配置读取、校验

- **必读**：[05](../05-config.md) 全文、[12](../12-ucode.md)「配置快照」、[02](../02-dataplane.md)「主机策略模型」中的冲突校验
- **产出**：`lib/schema.uc`、`lib/config.uc`、夹具（只包含 `expected/snapshot.json` 或 `expected/error.json`；运行器需要支持这两种期望文件，请顺带扩展 `tests/run.uc`）
- **要求**
  - 05 中的每个字段都在 `schema.uc` 中出现，字段名、类型、默认值、枚举逐一对应。新增或修改字段必须先改 05
  - 05「校验规则」中的 6 条全部实现。错误的 `field` 采用 `段类型[序号].字段` 或 `node.<段名>.字段` 的写法
  - 快照归一化规则见 12
- **夹具（至少）**：默认配置；完整配置（每个字段都显式设置一次）；以下每种错误一个夹具：`node` 不存在、host 缺少 ip 与 mac、`direct`+`udp=1`、两个 host 的 MAC 相同、
  `trust_dns` 有 3 个、非法 CIDR、vless 缺少 uuid、reality 缺少 pbk、枚举值非法
- **验收**：`ucode tests/run.uc` 通过；每个错误夹具恰好产生一个错误，且错误码符合预期

- **验收**：运行器通过；CI 中 `sudo nft -c -f` 检查每个期望文件都通过（T1.8 之前可以在本地虚拟机上手动验证，并把输出贴进 PR）

## T1.6 Xray 渲染器与出站映射

- **必读**：[06](../06-nodes-subscription.md)「Xray 配置渲染」「出站映射」、[05](../05-config.md) node 字段
- **产出**：`lib/render/outbound.uc`（节点 → 出站对象）、`lib/render/xray.uc`（完整配置）；夹具
- **要求**

  - `sni` 为空时，TLS 的 `serverName` 使用节点原始域名；节点地址本身就是 IP 且 `sni` 为空时不输出 `serverName`

- **夹具**：[11](../11-plan.md)「必备用例」中列出的 9 种协议 × 传输 × 安全层组合，每种一个；外加 `sniffing=0` 一个

## T1.7 `check` 与 `render` 子命令

- **必读**：[10](../10-cli-luci.md)「`aether-proxy` 约定」、[04](../04-lifecycle.md)「启动」第 2、3、5 步
- **产出**：`lib/cmd/check.uc`、`lib/cmd/render.uc`
- **要求**
  - `check`：读取 UCI 与数据 → 校验 → 用 `runtime = { node_ip: null, dns_tier: "T2", restored: {} }` 渲染四份产物到 `/var/run/aether-proxy/staging/` →
    `xray run -test -c`（找不到 xray 二进制时跳过这一项并在结果中注明）、`nft -c -f`。**不改动任何系统状态**（staging 目录除外）
  - 渲染 chinadns 前解析 `ctx.paths` 的全部 6 个路径（gfwlist、chnlist、apple 按「`/etc/aether-proxy/data/` 优先、否则包内基线」解析；proxy_domain、direct_domain 指向 custom 目录；boot_list 指向 `/var/run/aether-proxy/boot.txt`）。规则数据文件两处都不存在时报错退出，不准省略路径
  - 前置检查（[02](../02-dataplane.md)「内核与模块前提」、[01](../01-architecture.md)「组件二进制的查找顺序」）作为 `check` 的一部分实现
  - `render <xray|nft|chinadns|dnsmasq>`：把对应产物输出到 stdout，runtime 同上
  - 两个命令都支持 `--json`，格式见 10；退出码见 10
- **验收**（在 24.10.8 虚拟机上）
  1. `enabled=1` 但没有设置节点时 `aether-proxy check --json`：`ok` 为 false，错误为 `main.node` required（随包默认配置是 `enabled=0`，此时 `check` 返回 `ok: true`）
  2. 添加一个手动节点并设为 `main.node` 后，`check` 返回 0
  3. 执行 `check` 前后，`nft list ruleset`、`ip rule`、`/tmp/dnsmasq.*` 均没有变化（用 md5 对比）
  4. `aether-proxy render nft | nft -c -f -` 通过

- **验收**：`tests/host/ucode tests/run.uc` 与 `bash tests/cli/run.sh` 全部通过；`tests/ci/xray.sh` 对全部 `expected/xray.json` 通过（本地运行）

## T1.10 `--json` 模式下不输出人读提示（真机测试后追加）

- **分支**：`m1/check-json-quiet`
- **背景**：真机上 `aether-proxy check --json ... 2>&1` 的输出里，JSON 中间混入了 `ok: rendered and validated in …` 与
  `PRECHECK_FAILED: …` 这类人读提示（`lib/pipeline.uc` 的 `finish()` 在 `--json` 时把它们写到 stderr）。rpcd 以后会解析这些命令的输出，
  调用方也常常 `2>&1`，所以 `--json` 模式下除了那一个 JSON 对象之外，命令不应再向 stdout 或 stderr 输出任何内容。
- **必读**：[10](../10-cli-luci.md)「`aether-proxy` 约定」；`aether-proxy/src/lib/pipeline.uc` 的 `finish()` 及其所有调用方
- **要求**
  - `--json` 时：stdout 恰好一个 JSON 对象，stderr 为空（syslog 事件照常写，不受影响）
  - 非 `--json` 时行为不变
  - 适用于 `check`、`render --json`、`version --json`，以及今后所有支持 `--json` 的子命令（`finish()` 统一处理）
- **测试**：在 `tests/cli/run.sh` 中增加断言：`check --json` 的成功与失败两种情况、`render --json`、`version --json`，stderr 都为空，
  且 stdout 能被解析为单个 JSON 对象。
- **验收**：`tests/review.sh` 的 FAIL 为 0；新增的 CLI 断言全部通过。

## T1.11 Xray 渲染改用新版命名

- **分支**：`m1/xray-new-names`
- **背景**：Xray 26.9.30（项目要求的最低版本）的出站支持扁平写法，`streamSettings` 用 `method` 取代 `network`。设计决定一律使用新版命名，
  不为旧版本保留旧字段名（[06](../06-nodes-subscription.md)「出站映射」及其后的说明，2026-10-15 更新）。
- **必读**：[06](../06-nodes-subscription.md)「Xray 配置渲染」「出站映射」；`aether-proxy/src/lib/render/outbound.uc`、`render/xray.uc`
- **要求**
  - 四种协议的出站改为扁平写法：`settings = {address, port, id|password, …}`，不再输出 `vnext`、`servers`、`users`
  - `streamSettings.network` 改为 `streamSettings.method`
  - 其他字段与键顺序保持不变；键的插入顺序按 06 映射表书写顺序
  - 用 `tests/host/ucode tests/run.uc -- --update` 重新生成受影响的 `expected/xray.json`，**逐个核对 diff**：变化只能是上述两类改名与结构扁平化
- **验收**
  1. `tests/review.sh` 的 FAIL 为 0（本卡会修改既有期望文件，WARN 中列出的每个文件都要在报告里说明）
  2. `CI_TOOLS_DIR=/workspace/openwrt/ci-spike/tools bash tests/ci/xray.sh`：全部 `expected/xray.json` 通过真实 Xray 26.9.30 的 `run -test`
  3. 报告中贴出一个改动前后的出站对比（任选一个 vless reality 夹具）

## T1.12 chinadns-ng 写入的动态集合加 `flags interval`（真机窗口发现）

- **分支**：`m1/dynamic-set-interval`
- **背景**：2026-10-15 真机窗口中 `gfw` 模式完全失效：chinadns-ng 往 `gfw4` 写入 IP 时内核返回 EINVAL（`ipset_end_add_ip error when adding ip: (22) Invalid argument`）。
  chinadns-ng 总是把每个 IP 作为区间（起点 + 终点）写入，集合必须带 `flags interval`。设计已修正（[02](../02-dataplane.md) 模板与要点说明）。
  CI 的 chinadns-ng 校验只启动进程、不真正写集合，所以没能发现——本卡同时补上这个缺口。
- **必读**：[02](../02-dataplane.md)「nft 规则模板」与其后的要点；`aether-proxy/src/lib/render/nft.uc`；`tests/ci/chinadns.sh`、`tests/ci/common.sh`
- **允许改动**：`render/nft.uc`、受影响的 `tests/fixtures/t13-*/expected/aether-proxy.nft`、`tests/ci/chinadns.sh`（及必要时 `common.sh`）
- **要求**
  1. `gfw4`、`udirect4`、`uproxy4` 渲染为 `{ type ipv4_addr; flags interval; auto-merge; … }`，`restored` 元素照常写入。其他集合不变。
  2. 重新生成 t13 期望文件，逐个核对 diff：只能是这三个集合的定义行变化。
  3. `tests/ci/chinadns.sh` 创建 chinadns-ng 所需的集合时，动态集合也要带 `flags interval`（与设计一致；`chnroute4` 本来就带）。
  4. 在 `tests/ci/chinadns.sh` 中增加一项**真实写入**检查（只在 GitHub runner 上运行，不需要在本机跑通）：选一个 `gfw` 模式的夹具，
     把渲染出的配置中 `trust-dns` 改为 `tcp://8.8.8.8`（runner 在境外，可以直连），启动 chinadns-ng 后用 `dig @127.0.0.1 -p 31053 www.google.com A`
     查询，然后断言 `nft list set inet aetherproxy gfw4` 中至少有一个元素。runner 上没有 `dig` 时用 `apt-get install -y dnsutils`。
     失败时打印 chinadns-ng 的日志。
- **验收**：`tests/review.sh` 的 FAIL 为 0（WARN 中列出的期望文件要在报告中说明）；报告中贴出改动前后 `gfw4` 定义行的对比，以及 `chinadns.sh` 新增检查的代码片段。
  CI 中的真实写入检查由设计负责人推送后确认。
