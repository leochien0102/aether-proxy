## T2.0 规则数据基线与生成工具

- **分支**：`m2/data-baseline`
- **背景**：`aether-proxy/files/data/` 目前为空，包内没有规则数据基线，`data.load` 在真机上会因缺少规则数据而失败（[05](../05-config.md)「列表文件的解析规则」）。
  M2 上真机之前需要一份基线；同时，生成数据的逻辑以后也是 M7 发布通道 CI 的核心（[08](../08-updates.md)），所以这次就写成可复用的工具，而不是手工拼一份文件。
- **必读**：[08](../08-updates.md)「数据格式与来源」「`manifest.json`」之前的部分；[05](../05-config.md)「列表文件的解析规则」与「文件」；
  `aether-proxy/src/lib/data.uc`（设备端解析器——生成的文件必须能被它零错误地解析）；`aether-proxy/Makefile`
- **允许改动**：新增 `tools/data/`、新增 `aether-proxy/files/data/*`、修改 `aether-proxy/Makefile`（安装数据文件）、
  在 `.github/workflows/test.yml` 中**新增一个步骤**运行 `tools/data` 的单元测试（不改动已有步骤）

### 要求

1. **生成工具** `tools/data/build.py`（Python 3，只用标准库）：
   - 用法：`python3 tools/data/build.py --out <目录> [--cache <目录>]`。`--cache` 用于保存/复用下载的上游原始文件，便于离线重跑与测试。
   - 产出 5 个文件：`gfwlist.txt`、`chnlist.txt`、`apple.txt`、`chnroute4.txt`、`gfw_static4.txt`，格式严格符合 05「列表文件的解析规则」
     （每行一项、无注释、无空行、域名小写去首尾点、CIDR 不带主机位、`/32` 写成裸地址、排序去重、文件以换行结尾）。
   - 另外产出 `SOURCES.md`：每个文件的上游 URL、下载时间（UTC）、上游原始文件的 SHA-256、上游许可证、生成后的行数。
2. **上游与转换规则**（与 08 的表一致）：
   - `gfwlist.txt`：`https://raw.githubusercontent.com/gfwlist/gfwlist/master/gfwlist.txt`（Base64）。解码后按 AutoProxy/ABP 语法抽取域名：
     跳过 `!` 注释、`[AutoProxy …]` 头、`@@` 白名单、`/…/` 正则；`||example.com`、`|http(s)://example.com/...`、`.example.com`、
     裸 `example.com/path` 都取主机名；主机名中含 `*` 的条目跳过；IP 地址跳过；不能通过域名校验的跳过。跳过的条目按原因计数写进 `SOURCES.md`。
   - `chnlist.txt` / `apple.txt`：`https://raw.githubusercontent.com/felixonmars/dnsmasq-china-list/master/accelerated-domains.china.conf` 与 `apple.china.conf`，
     每行形如 `server=/domain/IP`，取 `domain`。
   - `chnroute4.txt`：`https://ftp.apnic.net/stats/apnic/delegated-apnic-latest`，取 `apnic|CN|ipv4|<起始>|<数量>|…` 的行；
     数量不是 2 的幂时拆成多个 CIDR（不能用一个更大的前缀去近似）；可以把相邻网段聚合，但聚合后覆盖的地址集合必须与输入完全相同。
   - `gfw_static4.txt`：手工维护的源文件 `tools/data/gfw_static4.src.txt`（放进仓库）。初始内容取 Telegram 公布的 IPv4 网段
     （`https://core.telegram.org/resources/cidr.txt` 中的 IPv4 部分），在源文件顶部注释里写明来源与日期；生成时去注释、规范化。
   - 下载用 `urllib`，失败要明确报错退出，不准静默生成空文件。
3. **合理性检查**（08 的表，任一不通过就以非零码退出，不写出任何文件）：行数下限、必含项（`google.com`、`baidu.com`、`apple.com`）、
   chnroute4 必须覆盖 `223.5.5.5` 与 `114.114.114.114`、不得覆盖 `8.8.8.8` 与 `1.1.1.1`。
4. **单元测试** `tools/data/test_build.py`（`python3 -m unittest`）：用小的内联样例覆盖 gfwlist 各语法分支、`server=/…/` 解析、
   APNIC 非 2 的幂拆分、聚合前后地址集合相等、`/32` 规范化、排序去重、合理性检查失败时不写文件。不访问网络。
5. **设备端兼容性校验**：生成后，用仓库的 `data.uc` 解析这 5 个文件，必须零错误。实现方式：写一个小的 ucode 脚本
   `tools/data/verify.uc`，用 `tests/host/ucode` 运行（`import { parse_domains, parse_cidrs } from 'aetherproxy.data'`，
   以 `data.uc` 的实际导出为准），报告每个文件的项数与错误数；有错误则以非零码退出。
6. **生成并提交基线**：运行工具，把 5 个文件和 `SOURCES.md` 放进 `aether-proxy/files/data/`；`aether-proxy/Makefile` 把 5 个 `.txt` 安装到
   `/usr/share/aether-proxy/data/`（`SOURCES.md` 不安装）。在报告里写明每个文件的行数与大小，以及包体积的变化。
7. **许可证**：README 规则 8 禁止复制第三方**代码**；这里提交的是第三方**数据**的转换结果，允许，但必须在 `SOURCES.md` 中逐个写明上游与许可证
   （gfwlist 为 LGPL-2.1，dnsmasq-china-list 为 WTFPL，APNIC 统计数据见其使用条款）。报告中单列一节说明。

### 验收

1. `python3 -m unittest tools/data/test_build.py` 全部通过
2. `python3 tools/data/build.py --out <临时目录> --cache <缓存目录>` 成功；用同一缓存再跑一次，输出逐字节相同（可复现）
3. `tests/host/ucode tools/data/verify.uc <目录>` 对生成的 5 个文件零错误
4. `tests/review.sh` 的 FAIL 为 0
5. 包能否编译、数据能否在真机加载，由设计负责人合并后用 CI 产物与 H28K 复测
