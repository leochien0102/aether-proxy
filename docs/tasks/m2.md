## T2.2 子进程监督

- **分支**：`m2/supervise`
- **必读**：[04](../04-lifecycle.md)「进程模型」；[09](../09-logging.md)「子进程日志」（S1 结论：`uloop.process`、继承 stdio、被信号结束时退出码也是 0）与事件码
  `CHILD_STARTED`、`CHILD_CRASHED`；[12](../12-ucode.md)「编码规则」；本文件「拆卡计划」中的测试方法
- **允许改动**：新增 `lib/supervise.uc`、`tests/unit/supervise.uc`、`tests/stubs/child/`（假子进程脚本）；`const.uc` 末尾追加 T2.2 区块
- **接口**
  ```js
  import * as sup from 'aetherproxy.supervise';
  let s = sup.create({ name: 'xray', argv: [ '/usr/bin/xray', 'run', '-c', '…' ], run_dir: '…',
                       backoff: [ 5, 10, 30, 60 ], stable_secs: 300, on_event: (kind, info) => {} });
  s.start();           // 拉起；已在运行时无动作
  s.stop(done_cb);     // 主动停止：TERM，1 秒后仍在则 KILL；子进程退出后调用 done_cb；取消待执行的重启
  s.running();  s.pid();
  sup.kill_stale(run_dir, name, match);   // cleanup 用：读 pid 文件，/proc/<pid>/cmdline 包含 match 才结束它
  ```
- **要求**
  - 用 `uloop.process` 拉起，子进程继承 stdio；pid 写入 `<run_dir>/<name>.pid`（经 `sys.write_atomic`），子进程退出后删除
  - 区分主动停止与崩溃：只有 `stop()` 期间的退出算主动停止；其余一律记 `CHILD_CRASHED` 并按 `backoff` 依次延迟重启，最后一档封顶重复使用；
    连续运行满 `stable_secs` 后退避序号归零。`on_event` 收到 `started`、`exited`、`crashed`、`restarting` 四种事件
  - 发信号经 `sys.run([ 'kill', … ])`；判断进程是否还在用 `/proc/<pid>` 是否存在
  - 测试中 `backoff`、`stable_secs` 可传小数值（例如 `[ 0.2, 0.4 ]`、`1`），uloop 定时器用毫秒换算
- **测试**（`tests/unit/supervise.uc`，每个用例在 `run(case)` 内跑一个独立的 uloop 循环直到结束或硬超时）：
  正常启停与 pid 文件生命周期；子进程自行退出 → 崩溃 → 按退避重启（核对两次重启的间隔）；退避期间 `stop()` 取消重启；子进程忽略 TERM → 1 秒后 KILL；
  稳定运行后退避归零；`kill_stale` 只结束命令行匹配的进程（用一个命令行不匹配的进程验证它不被误杀）。
- **验收**：`tests/review.sh` 的 FAIL 为 0；全部用例在 30 秒内跑完。

## T2.3 系统操作原语

- **分支**：`m2/apply`
- **必读**：[02](../02-dataplane.md)「机制选择」「nft 规则模板」及其后要点（动态集合必须带 `flags interval`）；[03](../03-dns.md)「dnsmasq 对接」「引导解析」「真机验证」；

- **允许改动**：新增 `lib/apply.uc`、`tests/unit/apply.uc`、`tests/stubs/bin/`（命令替身）；`const.uc` 末尾追加 T2.3 区块；`lib/net.uc` 只允许**新增**纯函数
- **上下文对象**：所有函数第一个参数是 `ctx = { root, bin_dir, run_dir, state_dir, lan_ifaces }`。`root` 为系统路径前缀（正式环境为 `''`，测试时为临时目录），
  `bin_dir` 非空时外部命令从该目录取（测试用替身），`run_dir`/`state_dir` 默认取自 `const.uc`。系统路径一律从 `const.uc` 的路径表经 `root` 拼接，不准写死。
- **函数**（全部幂等，返回 `{ ok, detail, … }`，失败时同时记事件；不准抛异常）
  - nft：`nft_load(ctx, file)`、`nft_delete(ctx)`（表不存在也算成功）、`nft_table_exists(ctx)`、`nft_flush_prerouting(ctx)`（故障放行）
  - 动态集合：`sets_export(ctx)` → `{ ok, sets: { gfw4: [...], udirect4: [...], uproxy4: [...] } }`，解析 `nft -j list set`；
    元素可能是单个地址、前缀或区间（`auto-merge` 会把相邻地址合并成区间），**区间要转换成最少的 CIDR 列表**（在 `net.uc` 新增纯函数 `range_to_cidrs(a, b)`），
    输出与 `ctx.runtime.restored` 的格式一致；`sets_save(ctx, sets)`、`sets_load(ctx)`（读后删除 `sets.save`）
  - 策略路由：`route_add(ctx)`（`ip rule` 不存在才添加；`ip route replace local default dev lo table <ROUTE_TABLE>`）、`route_del(ctx)`（删到不存在为止，并清空路由表）
  - dnsmasq：`dnsmasq_confdir(ctx)`（03：读 `<root>/var/etc/dnsmasq.conf.*` 的 `conf-dir=`；多个实例时选 `interface=` 与 `lan_ifaces` 匹配的那个；找不到返回 `DNSMASQ_CONFDIR_NOT_FOUND`）、

    `<state_dir>/node-ip.json` 的 LKG；成功且值变化时才写回（避免频繁写 flash）；`write_boot_list(ctx, domains)` 写 `<run_dir>/boot.txt`
  - 冲突检测：`conflicts(ctx)` → 正在运行的冲突服务名列表。判定：nft 表名匹配 `ss_spec`（ssr-plus）、以 `passwall` 开头（passwall/passwall2）、
    或存在名为 `clash`/`mihomo` 的进程（OpenClash）。判定方式若不可靠，标 `TODO(design)` 并在报告中说明
- **命令替身**（`tests/stubs/bin/`）：`nft`、`ip`、`resolveip`、`killall`、以及 `<root>/etc/init.d/dnsmasq`（由测试在假系统树中创建）。每个替身把 `$0 $@` 追加到 `$STUB_LOG`，
  按 `STUB_<命令>_RC` / `STUB_<命令>_OUT` 环境变量决定退出码与输出；`nft -j list set` 的输出由测试提供样例 JSON（含单地址、前缀、区间三种元素）

## T2.4 daemon 主体：启动、停止、cleanup

- **分支**：`m2/daemon`
- **必读**：[04](../04-lifecycle.md) 全文（「状态」「启动」12 步表、「进程模型」、「停止」、「等待网络」、「动态集合的导出与恢复」、阻塞调用的约定）；

  现有 `lib/supervise.uc`（T2.2）、`lib/apply.uc`（T2.3）、`lib/pipeline.uc`、`lib/state.uc`、`lib/cmd/check.uc`；本文件「拆卡计划」中的测试方法
- **允许改动**：新增 `lib/daemon.uc`、`lib/cmd/daemon.uc`、`lib/cmd/cleanup.uc` 并在入口分发；`lib/pipeline.uc`（允许传入 runtime）；`lib/sys.uc` 只允许**新增** `lock(path)`；
  `const.uc` 末尾追加 T2.4 区块；新增测试与 `tests/stubs/` 下需要的替身；`lib/cmd/check.uc` 只允许抽出可复用的前置检查函数，行为不变
- **要求**
  1. **runtime 可传入**：`pipeline.build(opts)` 增加可选的 `runtime`（`node_ip`、`dns_tier`、`restored`），不传时行为与现在完全一致（`check`/`render` 不受影响）。
  2. **锁**：`sys.lock(path)` 用 `fs.open` 加文件句柄的 `lock('xn')` 实现非阻塞排他锁，返回句柄（持有期间不关闭）或 `null`。锁文件为 `<root>/var/lock/aether-proxy.lock`。
  3. **`daemon [--boot]`**：严格按 04「启动」表的 12 步执行，每一步失败都按相反顺序回滚（等价于 cleanup），`state.json` 写 `error` 与失败的步骤名，记 `START_FAILED`，以非零码退出。要点：
     - 第 2–3 步复用 `check` 的配置校验与前置检查，并加上 `apply.conflicts()`：有冲突服务在运行时以 `PRECHECK_FAILED`（`missing=conflict:<名称>`）失败
     - 第 4 步（仅 `--boot`）：存在 IPv4 默认路由（`ip -4 route show default` 输出非空），并且对 `boot_check_targets` 任一目标的 TCP 连接在 3 秒内成功（ucode `socket`，非阻塞 connect）；
       每 5 秒重试，总时长 `boot_wait_timeout`；超时记 `NET_WAIT_TIMEOUT` 后继续
     - 第 5–6 步：渲染到 `<run-dir>/staging/` 并校验（`nft -c -f`、`xray run -test`），通过后整体提交为 `<run-dir>/current/`，`render_hash` 记入 `state.json`
     - 第 7 步：用 `supervise` 拉起 chinadns-ng（DNS 级别 T2 的配置）；第 8 步：`apply.dnsmasq_install`
     - 第 9 步：`apply.write_boot_list`（所有节点的域名）后 `apply.resolve_node(当前节点)`；成功则以 `node_ip` 重新渲染 xray.json 并 `-test`；
       失败（含无 LKG）→ 状态记 `degraded`，**跳过第 10、11 步**，直接进入第 12 步
     - 第 10 步：`supervise` 拉起 xray，5 秒内在 `<root>/proc/net/tcp` 中看到 `TPROXY_PORT` 处于 LISTEN（端口按十六进制解析）
     - 第 11 步：`apply.sets_load()` 取得 `restored` → 以它重新渲染 nft → `apply.nft_load`、`apply.route_add`
     - 第 12 步：释放启动锁，进入 monitor 循环骨架：`uloop.interval(30000, tick)`，`tick` 本卡为空函数（T2.5 实现）；状态写 `starting`
  4. **信号**（`uloop.signal`）：
     - `SIGTERM`/`SIGINT`：按 04「停止」顺序执行，**每一步都要执行，前一步失败也不跳过**：退出循环 → `sets_export` + `sets_save` → `nft_delete` → `route_del` →
       `dnsmasq_remove` → 停 xray 与 chinadns（`supervise.stop`，两者都退出后继续） → 状态写 `stopped`，记 `SERVICE_STOPPED`，以 0 退出
     - `SIGHUP`：本卡先实现为「完整停止再完整启动」（T2.6 改为增量重载），记 `TODO(T2.6)`
     - `SIGUSR1`：立即调用一次 `tick`
  5. **`cleanup`**：不依赖 daemon 存活的幂等清理：`nft_delete`、`route_del`、`dnsmasq_remove`、`supervise.kill_stale`（xray、chinadns，按命令行包含 `<run-dir>` 判定）、
     删除 pid 文件；`state.json` 写 `stopped`。daemon 每次启动的第 1 步之后也先执行一次 cleanup（04「进程模型」）。
  6. 事件：`SERVICE_STARTED`（`running`/`degraded` 首次确定时，本卡在第 12 步按是否跳过 xray 决定）、`SERVICE_STOPPED`、`START_FAILED`、`NET_WAIT_TIMEOUT`、`PRECHECK_FAILED` 均按 09。
  7. 所有外部命令带不超过 10 秒的超时（04）。
- **测试**（宿主机，新增 `tests/daemon/run.sh`，并在报告中说明 CI 应增加的一步，**不要改 `.github/`**）：
  - 用 `--sys-root <临时目录>` 搭假系统树（`/var/etc/dnsmasq.conf.cfg01411c` 含 `conf-dir=…`、`/etc/init.d/dnsmasq` 替身、`/proc/net/tcp` 由测试写入 31080 的 LISTEN 行、`/sys/class/net/br-lan`）
  - 用 `--bin-dir` 指向替身：`nft`、`ip`、`resolveip`、`killall`、`xray`、`chinadns-ng`（后两者是可被 TERM 结束的常驻脚本，`xray run -test` 直接返回 0），全部把调用记录到 `$STUB_LOG`
  - 场景：
    1. 正常启动：断言调用顺序为「chinadns 拉起 → dnsmasq 安装 → resolveip → xray 拉起 → nft 加载 → ip rule」，`state.json` 最终为 `starting`
    2. 发 `SIGTERM`：断言停止顺序与 `sets.save` 被写入，所有替身子进程都已退出，`state.json` 为 `stopped`，退出码 0
    3. `cleanup` 连续执行两次：第二次没有多余的副作用调用
    4. `nft -f` 失败（`STUB_NFT_RC`）：daemon 回滚并非零退出，`state.json` 为 `error` 且记录失败步骤，回滚后没有残留子进程
    5. `resolveip` 失败且无 LKG：状态 `degraded`，xray 未拉起，nft 未加载，chinadns 与 dnsmasq 片段在位
    6. 冲突：`nft list tables` 替身输出包含 `table inet ss_spec`：以 `PRECHECK_FAILED` 拒绝启动，系统状态无任何改动
    7. 锁：已有一个 daemon 持锁时，第二个以退出码 3（`BUSY`）退出
  - 每个场景有硬超时，整个脚本在 2 分钟内结束，结束时不留子进程
- **验收**：`tests/review.sh` 的 FAIL 为 0；`bash tests/daemon/run.sh` 全部通过；报告中贴出场景 1 与场景 2 记录到的调用序列。

## T2.5 monitor 循环（依赖 T2.4 合并）

- **分支**：`m2/monitor`
- **必读**：[04](../04-lifecycle.md)「monitor 循环」「故障语义汇总」「动态集合的导出与恢复」；[03](../03-dns.md)「DNS 级别」（切换规则）与「引导解析」第 5 条（节点 IP 刷新）；
  [07](../07-probe.md)「代理健康检测」；[05](../05-config.md) `probe` 段；[09](../09-logging.md) 相关事件码；T2.4 合并后的 `lib/daemon.uc`（`tick` 的接入点以它为准）
- **允许改动**：新增 `lib/monitor.uc`、测试；`lib/daemon.uc` 只改 `tick` 的接入与间隔调整；`const.uc` 末尾追加 T2.5 区块
- **结构**：
  - **纯函数** `next(state, obs, cfg) → { state, actions, events }`。
    `obs` = `{ now, table_present, xray_listening, chinadns_listening, proxy_ok|null, dns_ok|null }`；
    `state` 记录 `state`、`dns_tier`、`dns_failsafe`、各项连续计数、`t3_since`、`last_t2_retry`、`last_node_refresh`；
    `actions` 是有序的动作名列表：`nft_reload`、`nft_flush_prerouting`、`set_tier:<T1|T2|T3>`、`dnsmasq_remove`、`dnsmasq_install`、`refresh_node_ip`。
    规则完全按 04「monitor 循环」1–6 与 03「DNS 级别」（含：失败 `fail_threshold` 次判不健康、成功 `recover_threshold` 次判健康；T2 下 DNS 探测连续 2 次失败且 `allow_china_fallback` 才降 T3；
    T3 下每 5 分钟试回 T2；任何级别下代理连续健康即回 T1；`fail_open` 两种取值的不同行为）
  - **执行器** `tick(daemon)`：采集 `obs`（规则表用 `apply.nft_table_exists`；端口读 `<root>/proc/net/tcp`；代理健康用
    `curl --max-time <probe.timeout> -x http://127.0.0.1:<HTTP_PORT> <probe.url>`；DNS 探测仅在 T2/T3 时用 `resolveip -4 -t 5 <dns_probe_domain>`），调用 `next`，依次执行 `actions`：
    `set_tier` = 以新级别重新渲染 chinadns.conf → 重启 chinadns-ng（`supervise`）→ `apply.dnsmasq_hup`；`nft_reload` = `sets_export` → 渲染（带 `restored`）→ `nft_load`；
    `refresh_node_ip` = `resolve_node`，IP 变化时更新 `node_ip4`（整表重载）并重新渲染、重启 xray，记 `NODE_IP_CHANGED`
  - 间隔：`running` 时 30 秒，其他状态 10 秒；一轮累计超过 30 秒时跳过下一轮（04）；执行动作前取全局锁，取不到则跳过本轮
  - `state.json` 在每轮结束时更新（`state`、`dns_tier`、`dns_failsafe`、`last_probe`）
- **测试**：`next` 的表驱动单元测试覆盖每一条规则及其边界（阈值前一次、恰好达到、恢复）、`fail_open` 两种取值、T3 回 T2 的时间判定、各动作的顺序；
  执行器用 T2.4 的替身环境做 2–3 个集成场景（代理失败 3 次 → 降 T2 并重启 chinadns；xray 端口消失 2 轮 → 清空 prerouting；规则表被删 → 重载）
- **验收**：`tests/review.sh` 的 FAIL 为 0；新增测试全部通过。
