## M4-02 组件逻辑名与 JSON 兼容迁移（阶段 1：后端契约）

状态：**待实现**（2026-11-09 出卡）。阶段 1 只做"逻辑 id 与物理引擎分离 + JSON 双写兼容"，不改默认引擎、不改配置键、不改事件码、不改 LuCI。

- **单一目标**：让 `status`/`components` 的组件标识不再把"运行的是哪个 DNS 引擎"和"这一个逻辑组件"混为一谈；旧键在本阶段继续有效，旧客户端与旧 `state.json` 不被破坏。
- **分支**：`feat/m4.02-dns-component-id`

### 现场事实（2026-11-09，H28K，0.6.3-r7）

设备同时装有 `chinadns-ng 2025.08.09-1` 与 `aether-dns 2026.11.04-1`，`status --json` 输出：

```text
"components": {
  "xray":        { "path": "/usr/bin/aether-xray", "version": "26.10.31" },
  "chinadns-ng": { "path": "/usr/bin/aether-dns",  "version": "2026.11.04" }
}
```

即**逻辑键 `chinadns-ng` 指向的其实是 aether-dns 二进制**。原因在代码：`cmd/check.uc` 的 `find_component()` 对 DNS 引擎直接用逻辑名当文件名（`${bin_dir}/${name}`、PATH 里的 `${dir}/chinadns-ng`），设备是因为设置了 `main.chinadns_bin=/usr/bin/aether-dns` 才没有回落到真正的 chinadns-ng 包。

这条现场记录见[P1 验收](../validation/p1-h28k-r7-online-update-20261109.md) §5；本卡不重新操作设备。

### 已冻结的设计决定（实现者不得自行更改）

1. **逻辑组件 id**：新增 `dns`，作为 DNS 引擎的权威逻辑键；`xray` 不变。`chinadns-ng` 保留为**兼容别名键**，本阶段与 `dns` 同时输出、值深相等。
2. **引擎标识**：每个 DNS 组件项新增 `engine` 字段，取值 `"aether-dns"`、`"chinadns-ng"` 或 `null`。只由解析后二进制的 basename 判定，不执行命令、不读文件、不看版本号。
3. **双写不只在新启动**：`status` 读旧 `state.json`（只有 `chinadns-ng` 键）时必须在**输出**里补齐 `dns`；不得改写 `state.json`、不得改其 mtime。
4. **本阶段不动的东西**（写进报告，别顺手扩）：`main.chinadns_bin` 配置键名与默认值；二进制发现顺序与默认引擎；事件码及事件字段（`COMPONENT_MISSING`/`COMPONENT_TOO_OLD` 仍用旧 `component` 值）；版本闸门 `CHINADNS_MIN_VERSION`（属 M4-03）；日志过滤器 `aether-proxy-logfilter.awk`；LuCI 任何文件（阶段 2 再改展示）。

### 允许改动

- `aether-proxy/src/lib/const.uc`（只加常量与注释）；
- **新增** `aether-proxy/src/lib/component_id.uc`（纯函数模块，见 R2）；
- `aether-proxy/src/lib/daemon.uc`、`reload.uc`（**仅**写 `state.json` 的那一处，用新模块产出 `components`；查找循环、事件、闸门一律不动）；
- `aether-proxy/src/lib/cmd/components.uc`、`aether-proxy/src/lib/cmd/status.uc`；
- `tests/` 下相关单测、集成测试、golden 期望与驱动（**不得**放宽既有断言或删除 oracle）；
- `docs/01-architecture.md`（组件查找顺序一节）、`docs/04-lifecycle.md`（`state.json` 字段与 components 的 JSON 契约）、`docs/10-cli-luci.md`（`components` 子命令与概览页数据来源）；
- `reports/M4-02.md`。

不改 LuCI、不改 `package/`、不改 `files/` 脚本、不改版本号。

### 要求

1. **常量**：`const.uc` 新增 `DNS_COMPONENT = 'dns'`；`CHINADNS_COMPONENT` 保持原值 `'chinadns-ng'`，注释写明"旧逻辑 id／兼容别名，内部分查找、事件与请求仍用它，阶段 2 再评估迁移"。
2. **纯函数模块** `component_id.uc`，至少两个导出：
   - `engine(path)`：`null`/空串/非字符串 → `null`；basename 为 `aether-dns` → `"aether-dns"`；为 `chinadns-ng` → `"chinadns-ng"`；其它 → `null`。不做文件系统访问、不执行命令、不按版本号猜引擎。
   - `with_aliases(components)`：返回**新对象**，不修改入参。保证 `xray` 原样；`dns` 与 `chinadns-ng` 同时存在且**深度相等**；只有其一则复制另一；两项都带 `engine`（由各自 `path` 推导，`path` 缺失或 `null` 时 `engine` 为 `null`）。其它字段（`found`、`path`、`version`）原样保留。
   - 入参为 `null`/非对象时返回 `null`（不要造一个空对象冒充"没有组件"）。
3. **daemon 写状态**：`initial_state.components` 与重载写回都改用 `with_aliases(...)`。`state.json` 里从此同时有 `dns` 与 `chinadns-ng`。内部仍按 `[C.XRAY_COMPONENT, C.CHINADNS_COMPONENT]` 显式列表循环，**不要**改成遍历 `components` 的键（否则会多取一次版本、多发一次事件）。
4. **重载版本保留不变**：路径没变沿用原 `version` 的既有逻辑照旧；新增别名键不得让它把 `dns` 当成第二个组件重新执行 `-V`。
5. **`components --json`**：`components` 对象同时含 `xray`、`dns`、`chinadns-ng` 三个键；`found:false` 时两者都是 `{found:false, path:null, version:null, engine:null}` 且深相等；`ok` 字段与退出码不变。
6. **`components` 人类可读输出**：从两行改为 `xray: <version> (<path>)` 与 `dns: <version> (<path>, engine <engine>)`；不再单独输出 `chinadns-ng` 行；`engine` 为 `null` 时省略 `, engine …`；`not found` 时仍写 `dns: not found`。
7. **`status`**：输出 `components` 前做同样的规范化（覆盖旧 `state.json` 只有 `chinadns-ng` 的情况）；`state.json` 里没有 `components` 字段时（停止态）仍然不输出该字段，不能凭空补一个空的 `components: {}`；全程只读，不写回状态文件。
8. **本阶段事件不变**：`COMPONENT_MISSING`、`COMPONENT_TOO_OLD` 的 `component` 仍是 `chinadns-ng`。在 `docs/04` 与 `docs/10` 写清"`dns` 是权威逻辑键，`chinadns-ng` 是兼容别名，阶段 2 才迁移事件与 LuCI 展示"，避免下一个人误以为别名是笔误。**别名不是永久契约**：在 `docs/04` 同时写下退出条件——LuCI 与事件迁移完成、且经过至少一个正式版本后才删除旧键；本卡不删。

## M4-03a 引擎选择与按引擎下限（0.7.0 桥接版运行时）

状态：**已实现并合并** `b701170`（2026-11-10，复审通过）。设计依据 [engine-dependency-20261109](../design/engine-dependency-20261109.md) §2–§3、§4.2；

### 现状（2026-11-10 读码确认）

| 事实 | 位置 |

| 显式覆盖不可执行时返回 null（fail-closed，不回退 PATH） | 同上 |
| 启动闸门按**组件名**取最低值 | `daemon.uc` 的 `minimums`；`cmd/check.uc` 的 `min` |
| 只有 `XRAY_MIN_VERSION`、`CHINADNS_MIN_VERSION`，没有 aether-dns 的下限 | `const.uc:30-31` |
| `engine` 已能从路径 basename 判定 | `component_id.engine()`（M4-02） |
| `reload.plan()` 只比较渲染产物哈希，路径/版本变化不触发 `restart_chinadns` | `reload.uc:24-38` |
| **短路点**：`plan()` 为空时 reload 在 `if (!length(rough_plan))` 处直接返回，只刷新元数据 | `reload.uc:~465` |

### 已冻结的设计决定

1. **候选顺序**（显式覆盖优先，其次按存在性）：`main.chinadns_bin`（可执行时）→ `/usr/bin/aether-dns` → PATH 中的 `chinadns-ng`。
   测试用的 `--bin-dir` 顺序同理：`aether-dns` → `chinadns-ng`。
2. **没有失败回退**：选中哪个就用哪个；它起不来就是失败（与 xray 一致）。
3. **下限按引擎**：`aether-dns → 1.0.0`；`chinadns-ng → 2025.08.09`；engine 未知（自定义路径）→ 不设下限、信息性放行。
4. **reload 一致性**：组件路径**或版本**变化都必须重启对应子进程，且不允许被"空计划"短路。
5. 本卡**不改** `aether-proxy` 的包依赖（仍是 `+chinadns-ng`），也不改 `update.uc`。

### 要求

1. **候选顺序**在 `find_component()` 内实现，`--bin-dir` 与真实路径同一顺序；

## M4-03b 升级事务：引擎前置与跳过语义（0.7.0）

状态：**已实现并合并** `63f2c19`（2026-11-10，复审通过；返工一次，卡在复审中补入目标版本门）。设计依据 [engine-dependency-20261109](../design/engine-dependency-20261109.md) §4.3–§4.6；
依赖 M4-03a 已合并。本卡只做后端事务，**不含 LuCI 展示**（另卡）。

- **单一目标**：更新 proxy 组时，先保证 DNS 引擎的**运行时下限与包依赖同时满足**，再做 backend 安装；任一步失败回到"能启动的旧组合"。
- **分支**：`feat/m4.03b-update-prerequisite`

### 现状（2026-11-10 读码确认）

| 事实 | 位置 |
|---|---|
| 组更新入口 `package_update()`，组内 `update_together()` / `install_with_rollback()` | `update.uc` |
| 已装版本读取 `installed_version()` 用 `opkg status <name>` / `apk list -I <name>` | `update.uc:164` |
| 安装 `install_package(ctx, pm, path, previous)`；`previous=true` 时加 `--force-downgrade` | `update.uc:736` |
| 桥接步由 `bridge_plan()` 决定，命中时只装一步并返回 `BRIDGE_INSTALLED` | `update.uc` |
| 清单只校验 `schema == 2` 与签名；`build_result()` 只遍历 `UPDATE_PACKAGES`，**未知包名被忽略** | `update.uc:113`、`:351` |
| `aether-dns` 目前不在 `UPDATE_PACKAGES`，也不在（旧）清单里 | `const.uc` |
| 运行时引擎判定已就绪：`check.find_component()`、`component_id.engine()`、`component_id.min_version()` | M4-03a |

### 已冻结的设计决定

**触发条件（2026-11-10 复审补充，必须最先判断）**：只有**本次要安装的目标 backend 版本** ≥ `PREREQ_ENGINE_FROM_VERSION`（新增常量，值 `1.0.0`）时才进入事务。低于它的更新**完全保持现状**：不解析引擎、不查 `-V`、不装包、不产生 `prerequisite` 字段。
理由：0.7.0 的包依赖仍是 `+chinadns-ng`，此时若强制前置，只装旧 chinadns-ng 的设备（今天全部设备）会因 `pkg_ok=false` 且清单无 aether-dns 资产而被阻塞更新。

1. **双条件**：`skip = run_ok && pkg_ok`。两者独立，任一不满足都要走引擎步骤。
   - `run_ok`：按 daemon 同一顺序解析出的引擎存在，且（无下限 或 `version >= min_version(engine)`）。
   - `pkg_ok`：已装元数据中**有包提供 `dns-engine`**（不是"版本够"）。
2. **`pkg_ok` 读不到时视为不满足**（保守），不要用版本号代替 `Provides`。
3. **引擎步骤在任何 backend 安装之前**：包括 `bridge_plan` 命中的桥接步安装与普通组安装。
4. **三种情形**：首装（失败可卸载）/ 替换且有**精确恢复资产**（失败回装，不卸载）/ 无精确资产（`PREREQ_MANUAL_REQUIRED`，零安装）。
5. **跳过语义**：双条件满足就跳过；目标版本已是最新时整单返回"已是最新"，不装、不重启。
6. **`aether-dns` 暂不加入 `UPDATE_PACKAGES`**（是否进更新页主列表另有决定）；本卡只把它作为前置资产读取清单。
7. **不改** `--previous` 语义、不改 LuCI、不改事件码与字段、不改运行时引擎选择。

- `aether-proxy/src/lib/update.uc`（前置判定、引擎步骤、跳过与回滚、结果字段）

### 要求

0. **目标版本门**：先确定本次会安装的目标版本（桥接步取 `plan.next.version`，否则取所选资产版本）；`version_cmp(target, PREREQ_ENGINE_FROM_VERSION) < 0` 时直接走原有流程，不做任何前置判定。该判断必须发生在桥接分支与普通分支**各自确定目标之后、安装之前**，不得在拿到目标版本前下结论。
1. **已装元数据读取**：扩展一个只读助手返回 `{ok, version, provides[]}`；opkg 从同一次 `status` 输出解析 `Provides:`；apk 分支现状无法可靠取得 → `provides` 视为空并在报告中标注"25.x 未验证"。不得为此新增包管理器以外的二进制。
2. **前置判定是纯逻辑+可注入 IO**：判定函数接受"解析结果 + 已装元数据"，便于单测；运行期 IO 只做一次 `find_component` 与一次 `-V`。
3. **引擎步骤顺序**：在 `bridge_plan` 命中分支与普通组安装**之前**执行；`aether-dns` 从清单 `packages['aether-dns'].current` 取资产（不存在则视为无可自动安装来源 → `manual_required`）。
4. **首装**：下载 → 校验 size/sha256 → 安装 → 校验版本；失败则卸载本次装的包（旧 proxy 不依赖它）。
5. **替换**：安装前必须确认清单 `previous` 与已装版本（含 `-rN`）**精确一致**、架构与包格式匹配、能校验；满足才用 `--force-downgrade` 安装新包（日期版 → 1.0.0 是降级）。失败时用该 `previous` 资产回装并校验版本，**不卸载**。
6. **无精确恢复资产**：返回 `{ok:false, code:'PREREQ_MANUAL_REQUIRED', exit:1}`，`detail` 含人工迁移要点，**不执行任何安装**。
7. **跳过与幂等**：双条件满足时前置动作记为 `skipped`；目标 proxy 版本与已装相同且双条件满足时整单返回 `UPDATE_UP_TO_DATE`，不装、不重启、不写 `UPDATE_INSTALLED`。失败后重试只补缺的步骤。
8. **结果形状**：**产生事务时**，成功或失败的结果都带 `prerequisite: { package, version, action }`（未触发事务的更新不产生该字段），`action ∈ installed|skipped|rolled_back|manual_required`；`aether-dns` 的实际安装沿用既有 `UPDATE_INSTALLED` 事件。
