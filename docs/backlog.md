### 现有设计中要保持开放的地方

改动以下设计时，要确认不会妨碍将来的分流：

- **单个 Xray 进程多出站**：`xray.json` 中已有 `routing` 段和一个暂未使用的 `direct` 出站（[06](06-nodes-subscription.md)）。
  分流应当表达为「多个出站 + 路由规则」，而不是 helloworld2 那样每条规则一套进程。
- **nft 判定链**：`by_mode` / `proxy` 链是分开的（[02](02-dataplane.md)），可以在「代理」动作之前插入按集合打不同 mark、
  或 TPROXY 到不同入站端口的规则。
- **chinadns-ng 最多 6 个自定义组**，首版已占用 3 个（`uproxy`、`udirect`、`boot`）。按服务分流如果需要按域名填充集合，
  组数会成为限制，届时要评估把域名分流交给 Xray 的 sniffing + routing，而不是 DNS 层。
- **节点引用**：订阅更新时「被引用的节点保留为 stale」的逻辑（[06](06-nodes-subscription.md)）目前只检查 `main.node`。
  分流规则引用节点后，引用检查要扩展到规则，而不是另写一套。
- **节点身份稳定**：节点 ID 一旦生成就不变，正是为了让分流规则能长期引用节点。

### 已做的成本评估（流量与连接数）

- 推荐**按需读取、不在后台采样**：首页打开时随状态一起读计数器，速率由前端用相邻两次读数相减得到，不保存历史。
  - 代理流量：nft 中统计「路由器发往节点 IP」与「节点 IP 返回」的两条计数规则（内核维护，几乎零开销）。
  - 总流量：WAN 接口在 `/proc/net/dev` 中的计数；直连 ≈ 总量 − 代理。
  - 连接数：`/proc/net/tcp(6)` 中远端为节点地址的连接数（不开多路复用时即代理连接数）；总连接数读 `nf_conntrack_count`。
- 不推荐 Xray 的 stats API：每次查询都要另起一个 `xray api` 进程，在 ARM 设备上按 2 秒轮询开销过大，还要改 Xray 配置。
- 历史曲线如果要做：daemon 每分钟记一个点，存 tmpfs 环形缓冲（24 小时 1440 个点，几十 KB）。现有设计不妨碍以后加。

### 操作的现有实现路径

- 切换节点：改 `main.node` 后 reload（增量，只重启 Xray），之后**自动做一次健康检测**并在首页显示结果（仓库所有者确认）。reload 完成后发一次 USR1 即可，不需要新机制。
- 重启：重启整个服务（`/etc/init.d/aether-proxy restart`），不只重启 Xray（仓库所有者确认）。
- 测当前节点延迟：向 daemon 发 USR1，monitor 立即跑一轮代理健康检测，`last_probe` 几秒内更新（与首页显示的是同一个指标：经节点请求 `generate_204` 的耗时）。
- 更新订阅：`job start sub update`。
- 停用/启用：建议写 `main.enabled=0/1` 后触发 reload（`reload_service` 遇到 `enabled=0` 会停止服务，见 04「重载」），即**持久**停用，重启路由器后仍保持停用；
  按钮随状态显示「停用」或「启用」。是否还需要「临时停止、重启后恢复」的语义，设计时再定。
- 自动刷新的成本：每次刷新是一次 rpcd `status` 调用（读几个状态文件，加上流量计数的一次 `nft -j list`），开销很小。
  前端经 `/ubus` 调 rpcd，**不受** uhttpd `max_requests 3` 的限制（源码核实：该上限只作用于 cgi/ucode/lua 这类脚本处理器，超出的排队而不是拒绝；ubus 处理器不计入）。
  要注意的是 rpcd 串行处理调用：每次调用必须很快，间隔下限建议 2 秒，同一时刻只允许一个刷新请求在途，上一次没回来就跳过本次；页面不可见（`document.hidden`）时暂停刷新。

### 现有设计中要保持开放的地方

- 首页需要的数据应当都能从现有只读接口取得：`status`（`state.json`、`probe.json` 摘要、`updates_available`）、`events`、`sub.json`；
  新增接口时优先扩展这些输出，而不是让前端直接读文件（[10](10-cli-luci.md) rpcd 插件）。
- 长任务（节点检测、订阅更新）只能经作业机制发起与轮询（[10](10-cli-luci.md)「作业机制」），首页上的按钮也不例外。

## B3 `fail_open=0` 且 Xray 缺位时的失败形态（待真机验证）

- 状态：观察项（2026-10-15 复审提出），不是缺陷。
- 情形：节点解析失败进入 `degraded` 且 `fail_open=0` 时，nft 与 ip rule 已安装而 Xray 未运行（04 第 9 步）。
- 待验证：代理目标的 TCP 连接是**立即被拒绝**（TPROXY 找不到监听 socket，包经表 233 送入本机，无 socket 时内核回 RST），还是**挂起直到超时**。
  下次真机窗口顺带测：让节点解析失败（错误的节点域名）+ `fail_open=0`，在 LAN 上 `curl -m 10 https://ipinfo.io/ip`，看耗时与报错。
- 若为挂起：考虑在 Xray 缺位时给 proxy 链加 `reject with tcp reset`（快速失败），属新的设计决定。
