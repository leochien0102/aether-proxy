# 取消候选（RC）通道（2026-11-19 定）

## 结论

不提供"候选通道"：没有 `main.update_channel`、没有 `channel-rc` 清单、界面不提供"检查候选更新"。
只保留一条更新通道（`channel-stable`）。预发布 Release（`v<ver>-rcN`）仍可打，但只是**给人手动下载/安装**的
发布物，不进入任何通道，也不被客户端检查。

## 为什么

需求里同时出现了两条互斥的诉求：

1. 候选与正式是**同一批字节**（`promote-rc` 逐字节校验、sha256 相等）
2. 正式的**版本号高于**候选（装过候选的设备要能"再更新一次"）

版本号写在包内（`control` 的 `Version:` 与 `const.uc` 的 `RAW_VERSION`），所以"逐字节相同"必然意味着"版本号相同"，
第 2 条自动不成立；反过来，只要让版本号不同，两条诉求就无法同时满足。

### opkg 的排序实测（H28K，OpenWrt 24.10.5）

用自建假包在设备上实测 `opkg install` 的行为（候选 → 正式）：

| 候选版本 | 正式版本 | opkg 结果 |
|---|---|---|
| `1.2.2-rc1` | `1.2.2-r1` | `Not downgrading`（rc1 被认为更新） |
| `1.2.2-r1-rc` | `1.2.2-r1` | `Not downgrading` |
| `1.2.2.rc-r1` | `1.2.2-r1` | `Not downgrading` |
| `1.2.2~rc1` | `1.2.2-r1` | `Upgrading` |
| `1.2.2-r1~rc1` | `1.2.2-r1` | `Upgrading` |
| `1.2.2-r1` | `1.2.2-r2` | `Upgrading` |

规律：opkg 逐字符比较，**只有 `~` 能压序**；任何"加在正式号后面"的尾巴（`-rc1`、`-r1-rc`）都因为"前缀相同、串更长"
被判为更新。而 git 标签不允许 `~`，`v1.2.2~rc1-rc1` 打不出来，需要额外维护"包版本 ↔ 标签名"的映射。

本仓自己的 `version_newer()` 与 opkg 在其中三种写法上判断相反（`version_parts()` 把 `-rc1`、`-r1-rc` 都折成 release 0），
于是会出现"界面说有更新、opkg 拒绝安装"的组合；`1.2.2.rc-r1` 更糟：两边都判成"无更新"或"降级"。

## 被否掉的替代方案

- **`~rc1` 候选 + 标签解耦**：opkg 顺序正确，但要给 `rc.sh` 增加"包版本 ↔ 标签名"映射，且正式版仍需重新构建（非同一批字节）。
- **`-rc1` 候选 + 一律 `--force-reinstall`**：能装上，但放弃 opkg 的版本序兜底，且同样不是同一批字节。
- **版本递增 `r1` → `r2`**：opkg 天然认可，但正式版不是候选那批字节，"晋升同一产物"名不副实。

## 回退范围

- 客户端与后端：T16.34（`main.update_channel`、候选清单拉取与合并、预发布徽标、rpcd `set_update_channel`、CLI `--channel`）
- 发版工具与 channel 仓：T16.35（`rc.sh`、`promote-rc.sh`、`publish_target=rc`、`channel-rc` 分支）

保留：`promote` 的"正式 Release 输入"模式（T16.30 的另一半能力），以及"正式版逐字节晋升"这条保证。
