# 更新链数据化与自动续步（2026-11-11）

状态：**设计已定**（2026-11-11，仓库所有者提出"链放仓库、按链安装"）。实现见 M4-07；
0.6.3 的一次性链登记见"立即动作"。

## 1. 现状：链已经是数据，不是硬编码

签名清单的 `compatibility.aether-proxy` 就是链：

```json
{ "from": "0.6.3", "target": "1.0.0-r1",
  "required_steps": ["0.7.0-r1"],
  "steps": [{ "version": "0.7.0-r1", "min_from": "0.6.3", "assets": {...}, "reason": "..." }] }
```

设备端的 `bridge_plan()` 读取它、校验顺序与资产、选出下一步。缺的不是"把链放仓库"，
而是**通用执行器**：装完一步后，由刚装好的新 CLI 继续下一步，直到 target。

## 2. 为什么必须由新二进制续步

每一步的安装与检查语义由那一步的代码决定（0.7.0 有事务、1.0.0 的包依赖变了）。
旧进程只应做调度：装好下一步 → **重新执行 `/usr/bin/aether-proxy`**（`update package` 契约在
docs/08「更新接口（固定）」里冻结）→ 读它的结果决定继续还是结束。旧进程不解释新格式。

## 3. 自动续步的语义

在 `update package` 内循环：

1. `bridge_plan()` 选出下一步 → 安装该步后端（只后端，不装页面包）→ 重启并检查；
2. 若 `steps_remaining > 0`：`sys.run([新 CLI, 'update', 'package', <包>])`，把它的结果作为本步结果向上传递；
   **续步必须重新下载并验签清单**（不复用内存里的旧链）：链在仓库里是可更新的数据，每一步都按当下的
   签名清单重新计算下一步，这样渠道侧更新链后设备无需改代码即可跟随；
3. 到达 target：由 target 版本的自身逻辑执行（1.0.0 是前置事务 + 组更新）；
4. 结束条件：`code != BRIDGE_INSTALLED` 或已到 target。

约束：

- **总预算**：一个作业共享 `JOB_TIMEOUT_SECS`（600 s）；每步重启约 10–12 s，2–3 步足够；
  超时返回明确 code（`BRIDGE_INCOMPLETE`），设备停在最后一个已发布版本，重试即从 `installed` 续跑。
- **防循环**：循环次数 ≤ `required_steps` 长度；每步必须让已装版本严格前进（`bridge_plan` 已校验顺序）。
- **幂等**：已装版本已在该链上就跳过已完成步骤；`installed >= target` 直接返回 `UPDATE_UP_TO_DATE`。
- **失败即停**：某步失败不继续；已成功步骤视为完成，不回滚（回滚只发生在单步内部）。
- **安全**：链在签名清单里，资产逐个校验 hash/size；不引入新的信任根。

## 4. 链的维护流程（每次发布）

- 出现"目标版本需要先有某个更新器"的跳跃时，在渠道仓库加一步（version/min_from/assets），
  同步 `required_steps`；资产复用已发布包，`publish.sh` 识别"已发布且字节一致"不重传。
- 例：2.0.0 若需要 1.x 的更新器，链加一步 `1.x`（min_from 0.7.0）。0.7.0+ / 1.0.0 设备
  一次点击自动走完；0.6.3 设备先经过 0.7.0（见下），之后同样自动。
- 链只增不改：已发布步骤的版本/资产不得修改，否则设备端 `bridge_plan` 会判为无效。

## 5. 0.6.3 的一次性边界

`v0.6.3-r7` 的 `bridge_plan` 执行完一步就把 `BRIDGE_INSTALLED` 返回并停止（已发布，无法回改），
所以存量 0.6.3 设备**只能两击**：第一次装 0.7.0 后端，第二次由 0.7.0 的事务升到 1.0.0。
登记 0.6.3 → 0.7.0 的链即可免手工；之后的所有跳跃都由 0.7.0+ 的自动续步覆盖。

## 6. 决定与后续动作

**0.6.3 不登记兼容链**（2026-11-11，仓库所有者）：存量仅一台家庭 x86 VM 与一台朋友的 H28K，
手工安装 0.7.0 再更新到 1.0.0 即可，或直接刷完整固件。因此 `channel-stable` 清单保持无
`compatibility` 链；0.6.x 在页面上会看到 1.0.0 并因 `dns-engine` 依赖失败，属已知边界（文档写明
0.x 不能直升 1.0.0）。

后续动作：

1. 实现 M4-07（自动续步），随下一个正式版（1.0.1 / 1.1.0）交付；之后的新跳跃只需在渠道加一步数据；
2. 用 0.7.0 环境验证 M4-07 的单次点击两跳（0.7.0 → 1.0.0 已由 H28K 手工引擎迁移验证过）；
3. 若将来 0.7.0 之前的存量变大，再回头登记对应链（数据改动，不改代码）。

## 7. 备选方案评估：独立 update 服务（2026-11-11）

仓库所有者提出"做一个独立的 update 服务、与应用解耦"。评估结论：**现在不做**，作为家族扩大后的候选；
先由 M4-07 拿到"驱动稳定"的主要收益。

**收益**：驱动不随应用版本变化；应用装坏时仍可修复；多个 aether-* 组件共用一套更新机制。

**局限（三条硬约束）**：

1. 存量 0.6.3 仍需一次人工——服务不在旧设备上，与 M4-07 的边界相同。
2. **自更新鸡生蛋**：服务自己也要能升级；若它需要不兼容变更，旧服务同样走不了新链。要避免，它必须极小、
   只做通用动作，并且自身也用同一套链机制升级。
3. **策略仍在应用里**：重启后等健康、页面包必须在后端校验通过之后才装、引擎虚拟包与版本下限——
   这些判断独立服务要么复制（双份维护），要么回调应用的冻结 CLI（那就仍跑应用代码，只是多一层 IPC）。

**触发条件**（满足任一才重新评估）：

1. aether-* 家族继续扩大，出现第二个/第三个需要同一套更新机制的独立应用；
2. 出现"应用被装坏、应用内更新器无法运行"的真实场景，需要外部修复/降级；
3. 更新驱动本身需要做出不兼容变更，M4-07 的"只做通用动作"约束无法维持。

**若触发，形态**：`aether-update` 只做传输与安装（清单验签、下载与 hash/size 校验、调包管理器、重启、
调用 `aether-proxy check` 等冻结接口），**不自带业务策略**；策略通过版本化的 CLI 接口回调目标应用。
