## 实现

在 `aether-proxy/files/aether-proxy.init` 的 `procd_open_instance aether-proxy` 后添加：

```sh
procd_set_param limits nofile="1000000 1000000"
```

该参数无 target 条件，设置 procd 托管 daemon 的软/硬 FD 上限，由其启动的 xray 子进程继承。修复针对游戏模式 UDP 高并发时低 FD 上限引发所有 inbound `accept4` EMFILE 的全平台缺陷；x86 只是先复现的平台。需要重启服务以使新进程获得上限，单纯 HUP 不会改变已有进程的限制。

`tests/ci/smoke.sh` 对安装后的 `/etc/init.d/aether-proxy` 检查完整参数行，真实固件安装及 host fake-root 都使用该断言。`tests/ci/smoke-host.py` 在 opkg/apk 两种场景中验证断言成功，并注入缺失参数行、退回 `4095 4096` 两种错误，验证 smoke 必须失败。

## 未完成的环境验收

- Host smoke 使用包管理器 stub 和源文件构造安装根，不代表真实 ipk/apk 已构建、安装通过。本环境没有 Docker/Podman，未执行真实固件六格安装矩阵或 SDK 打包；打包工作流/发布资产静态回归已通过。
- 本环境没有 BusyBox，smoke 的 `sh` 语法检查已通过，BusyBox ash 检查未执行。
- 未提供目标设备地址/连接信息，因此未连接设备，未验证实际 xray FD 上限，也未进行 x86 游戏模式 UDP 高并发压测；不能据本地静态测试声称 EMFILE 已在真机消失。

设备安装并重启服务后应执行：

```sh
cat /proc/$(pidof aether-xray | awk '{print $1}')/limits | grep 'open files'
```

预期软/硬上限均为 `1000000`。随后在 x86 开启游戏模式 UDP 并复测原高并发场景，确认不再出现 `accept4: too many open files`。其他 target 同样需要确认继承的实际限制。

## 复审补充：H28K 实机验证

主会话在 H28K（aarch64，OpenWrt）上安装了 T13.1 构建的 `aether-proxy_0.6.3-1_all.ipk`：

```text
Max open files            1000000              1000000              files
```

证明 `procd_set_param limits` 确实传递到 xray 子进程，且不只是静态断言。

验证后已用正式 0.6.3 包恢复 H28K，xray 回到：

```text
Max open files            4095                 4096                 files
```

x86 游戏模式 UDP 高并发场景仍需在 x86 真机上复测；H28K 只证明 procd limit 生效，不代表 x86 的 FD 增长问题已根因解决。
