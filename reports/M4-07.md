## 复审修订：预算边界与 flash 安全

### 改动及阈值理由

依复审意见在原 worktree、原分支继续修复：

1. `UPDATE_CHAIN_MIN_BUDGET_SECS = 180` 为唯一准入阈值。`install_target()` 在引擎前置事务之前检查；普通后端、引擎及 companion 在下载完成、`UPDATE_STARTED` 和装包命令之前再次检查，避免下载耗时后仍盲目开始写入。不足时清理已下载临时资产，返回原有 `BRIDGE_INCOMPLETE`，不发出该次安装或 restart。
2. `install_package()` 直接调用 `sys.run(..., { timeout: C.JOB_TIMEOUT_SECS })`，opkg/apk 正向和回滚一律保持原上限 600 秒。预算不再控制已经开始的 flash 写入何时中断。
3. 通用命令适配器不再使用 `min(原上限, 剩余预算)`；已准入步骤的检查及失败恢复也保留各自原始超时，避免预算耗尽本身诱发健康检查失败、阻碍精确回滚。回滚属于已准入事务的恢复，不受新的安装准入门禁阻断。
4. handoff 在启动新 CLI 前应用同一 180 秒门禁；不再给该子进程套剩余预算的祖先计时器，否则即使子进程的装包命令保留 600 秒，祖先仍可能中途终止它。新 CLI 自行按继承预算准入，重新拉取并验签；它的各外部命令仍有原命令级上限。
5. 已准入步骤允许在调度截止时间之后完成验证/恢复，但不会因剩余不足再准入新安装或新 handoff。600 秒在此是共享调度预算，不是强制截断正在进行步骤的硬实时承诺；装包本身仍受原有 600 秒命令上限约束。
6. 更新 `docs/08-updates.md` 明确上述语义。链格式、`bridge_plan()`、步数门禁、严格前进、失败即停、事件注册及文案均保持不变；现有重启 helper 的命令适配器断言未改。

**为何取 180 秒**：采用复审建议的三分钟保守准入下限，给正常约 10–12 秒的步骤以及原 90 秒 restart、35 秒 check 和元数据/下载操作留出余量。它不是装包或整步最坏耗时的数学上界；慢 flash 的安全来自保留原命令超时，而不是把写入强塞进剩余预算。阈值用常量集中维护，测试不通过改小生产阈值加速。

### 边界

handoff 子进程不再设祖先超时，父进程依赖子进程自身的命令超时；若子进程异常挂起，作业会保持运行中，这是为了避免中途砍断 flash 写入而接受的代价。

**恰好等于阈值**：门禁表达式是 `budget_left() >= 180`。在门禁读取时恰好剩余 180.000 秒，允许开始；179.999 秒拒绝，180.001 秒允许。时钟测试固定在 10.500 秒，分别使用截止时间 190.499 / 190.500 / 190.501 验证。生产中若调用者设置 `deadline = now + 180` 后又经历验签/下载，抵达安装门禁时已经少于 180 秒，则正常拒绝，不会因曾经等于阈值获得豁免。若已在/超过 target，没有需要开始的新步骤，继续保持 `UPDATE_UP_TO_DATE` 语义。
