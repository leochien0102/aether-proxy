# T11.16 完成报告（app）

把 T11.14/T11.15 的 compatibility 能力接进真实发布链路：RC 携带受审的
`bridges/compatibility.json`，channel promote 下载并逐字节校验历史 bridge 资产，
publisher 收到同一份文件与字节后签名发布。不升版、不 push、不打 tag、不实际发布。

  `0.6.2-1 → 0.6.3-1` 单步（不杜撰中间版本），ipk 资产是已发布
  `aether-proxy_0.6.3-1_all.ipk` 的真实 sha256/size（取自 h28k-test/pkg063 的
  发布同源副本；docs/releases/0.6.2.md 明确「包与通道产物同源、同 hash」）。

  只含 ipk，作为待补齐草稿：promote 的每步 ipk+apk 检查会拒绝它，任何人都无法
  把半成品链晋升出去；`reason` 字段向设备用户说明 chinadns-ng 手工前置
  （docs/08 迁移表）。

### channel `.github/workflows/promote.yml`（channel 分支）

- 下载/校验步骤：rc-manifest 若带 `compatibility` 绑定，则预期资产集 22→23，
  校验绑定名合法性；全部 RC 校验通过后，读取 compatibility 文件，对每步每资产：
  - 元数据检查（url 形态、sha256 格式、size 为正）；
  - 字节来源：url 匹配本 RC 的 noarch aether-proxy 产物（按通道规则取
    aarch64_generic 字节）→ 从 RC 取；否则从既有 `channel-stable` 按名下载；
    两者都没有 → 明确报错立即失败（先于 preflight/签名/任何 release 操作）；
  - 下载后逐一校验 sha256/size；
  - 每步必须 ipk+apk 齐备（aether-proxy 是 noarch 双格式，缺格式会让该格式设备
    全部 BRIDGE_UNAVAILABLE，因此按硬性要求拒绝）；
  - 通过后把 `bridge/compatibility.json` + 全部字节写入 `bridge/`，经
    `GITHUB_ENV` 导出 `COMPATIBILITY_FILE`。
- preflight 步骤带 `--compatibility "$COMPATIBILITY_FILE"`，与最终发布同一份输入。
- 不 checkout app 源码、不执行 SDK/make/编译（contract 测试继续断言）。
- `scripts/publish.sh` **无改动**：T11.15 已实现 URL 集合/清理保留、
  `COMPATIBILITY_FILE` 校验与传递，本卡全部要求其已满足。

## 偏差与待定

- **提交的 `bridges/compatibility.json` 是诚实草稿**：apk 资产离线不可得，文件只含
  真实 ipk 字节。promote 的 ipk+apk 硬性检查使其不可能被晋升；冻结契约
  （`tests/compat/update-contract.json` 的 `bridges: {}`）因此保持有效。维护者在真正
  打 RC tag 时以 25.12 SDK 产物补齐 apk 并重新审核全链。备选方案（杜撰 apk hash、
  或不提交文件）分别违反「不能猜测」与任务卡「新增受审文件」的明确要求，故弃用。
- **build.py 未加 ipk+apk 完整性检查**：`tools/channel/build.py` 不在本卡允许改动
  清单内。promote 路径已强制；T11.15 的手工 `publish.sh` 路径仍依赖维护者审核。
  建议后续卡把该检查下沉到 builder。
- **发现既有隐患（未改，超出本卡范围）**：`release-candidate.yml`/`promote.yml` 期望
  ipk 文件名版本为 `<PKG_VERSION>-r<PKG_RELEASE>`（如 `0.6.3-r1`），但真实发布产物
  （h28k-test/pkg061-063）中 aether-proxy/chinadns-ng/aether-xray 的 ipk 名为
  `<PKG_VERSION>-<PKG_RELEASE>`（如 `0.6.3-1`），仅 luci-app 带 `-r1`。首次真实 RC
  构建可能在版本比对处失败。本卡测试沿用了仓库既有 fixture 约定（`-r1`），未改该
  逻辑。真实打 tag 前需要先核实 SDK 实际命名。
- RC 终点步校验比较的是**构建产物的版本字符串**（来自文件名解析），不是 tag 推导的
  `v<version>-r<release>`，因此对上述 `-r1/-1` 差异不敏感，只会拒绝真正过期的链。
- `promote.yml` 新增对 `GITHUB_ENV` 的依赖（步骤间传 `COMPATIBILITY_FILE`）；测试
  harness 在 `run_step` 中以 Actions 相同语义回放该文件。
