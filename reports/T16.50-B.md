## 实现与边界

1. 手动 `stats quota set/clear` 共用入口包装；LuCI `stats_quota` 经现有 CLI 适配器自然获得相同语义，无需改 RPC/LuCI 接口。
2. 只有 `ok == false && op == 'lock' && retryable === true` 才重试；不匹配错误文案，不把锁路径打开失败、mkdir/read/parse/write 错误当作锁竞争。
3. 最多 11 次单次非阻塞事务；相邻重试等待 100 ms，累计主动等待最多 1000 ms。每次重新执行完整取锁/读最新账本/合并/原子替换事务，不复用失败尝试的账本或配额时间戳。此为主动等待预算，不是任意底层文件系统阻塞时的硬实时保证。
4. 中间锁忙不记事件；最终失败仅记一条 error 级 `FS_FAILED`，使用底层 `op`（未显式提供时为 `write`）。成功不误报。原来写操作的 load warning + 统一 write error 双重记录已消除。
5. 读取或解析失败立即返回，不覆盖、不重试解析。只读 quota show 保持既有 warning 语义。底层事务仍然是单次非阻塞，未在共享底层引入 sleep/重试。
6. 修正既有 CLI 断言：账本路径为目录时实际失败于读取，应该归因为 `read`，不是 `write`。

## 同步屏障验证

新增入口：`python3 tests/stats/quota-retry.py`，已接入 `bash tests/stats/run.sh`。

- 测试运行真实 CLI 分发及真实 flock；模块仅复制到临时目录。测试观察器记录每次完整事务的结果，首次事务结果经独立 pipe 通知父进程，并阻塞于 gate pipe。产品代码不包含测试钩子。
- 父进程先持有稳定 sidecar 锁，再启动命令；收到明确 `op: lock, retryable: true` 后才决定释放或继续持锁。没有固定 sleep 决定竞争顺序，生产的 100 ms 等待是真正被测逻辑。
- 持续锁忙计时从父进程放行屏障开始；断言 11 次事务、0.8–3 秒内终止；进程通信另设 5 秒死锁防护。
- 实际写失败通过私有 `sys.uc` 观察器在正确的 `.tmp.<pid>` 路径创建残留目录，触发原始 `write_atomic` 的独占创建失败；不伪造写入函数返回值。

以下 **7 种场景对 set 和 clear 各执行一次，共 14 例**：

| 场景 | 完整事务次数 | 预期结果与事件 |
| --- | ---: | --- |
| 首次锁忙后释放短锁 | 2 | 原命令成功；无 FS_FAILED；配额正确，days/updated_at/未知字段保留，0600 |
| 全程持续持锁 | 11 | 有界失败；仅一条 `op: lock`；账本字节不变 |
| 初始非法 JSON（含 NUL） | 1 | 仅一条 `op: parse`；原始字节不变 |
| 首次锁忙后，持锁方留下非法 JSON 再释放 | 2 | 仅解析一次并立即失败；仅一条 `op: parse`；不继续重试、不覆盖 |
| sidecar 路径是目录 | 1 | 非竞争锁失败不重试；仅一条 `op: lock`；账本字节不变 |
| 账本路径是目录 | 1 | 不重试；仅一条 `op: read`；目录不变 |
| 原子写临时路径独占创建失败 | 1 | 不重试；仅一条 `op: write`；账本字节不变 |

所有失败场景还核对：退出码 1、单个 JSON `FS_FAILED` 响应、stderr 为空、事件 path/detail 与实际失败一致、事件总数恰好为 1。
