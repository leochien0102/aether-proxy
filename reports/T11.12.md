## RC 资产合同

1. `vVERSION-rcN` 或 `vVERSION-rRELEASE-rcN` 绑定源提交的 `PKG_VERSION` / `PKG_RELEASE`、目标正式 tag `vVERSION-rRELEASE` 和完整 commit SHA；包版本不含 RC 后缀。
2. 四份 SDK artifact 必须分别包含 aether-proxy、LuCI、zh-cn i18n、aether-xray、chinadns-ng，覆盖两架构和 ipk/apk，共 **20 包**。拒绝缺失、重复、意外包、架构和版本不符；翻译包使用原 po 版本，要求跨整个矩阵一致。
3. RC 保留两份 noarch 构建（即使字节不同），用架构前缀防止扁平资产重名；GitHub 不支持的字符归一化，原始文件名保留在清单中。
4. `rc-manifest.json` 绑定每个矩阵槽位、原始文件名、版本、sha256；`SHA256SUMS` 覆盖 20 包和该 JSON。只在所有校验成功后调用 `gh release create --verify-tag --prerelease --latest=false`，不创建正式 Release。已有 RC 不覆盖，失败残留不自动删除。

## 晋升合同

- 检查 app Release 是公开 prerelease、tag 精确匹配，解析轻量/附注 tag 到 commit，核对 RC 清单绑定。
- 只下载该 commit 的两个独立发布工具及四份 Makefile 版本元数据，不 checkout app；不执行 SDK、make、Go、gcc 或编译 usign。usign 使用系统安装包。
- 校验资产集合严格为 22 文件、矩阵完整、文件名安全、架构、源版本、正式目标、跨矩阵版本以及两层 sha256，然后才构造 `packages/<arch>/rc/<original name>`。
- 预检调用现有 `tools/channel/build.py --packages packages --out preflight`。下载已有 stable 资产；已有同名包不同字节，或已有同版本清单资产不同，均在签名/发布前失败。release 列表分页读取；查询失败不当作 stable 不存在。
- 与原 packages/data 发布共享 `channel-publish` 并发锁，防止通道内并发覆盖。
- 最后调用现有 `scripts/publish.sh publisher packages`，保留规则数据生成、旧签名验证、签名后验证、资产上传和清单切换行为。私钥只在最后一步由 channel Actions Secret 注入，不落入仓库或日志。
- noarch 按现有生成器的路径排序选 `aarch64_generic` 产物，正式通常 **14 个包文件**。二进制 apk 加架构后缀、翻译文件名归一化只改变名称，不改变包字节。测试逐项验证 stable 资产 hash 以及字节确实来自 RC。

## 兼容与明确边界

1. **未来正式 tag 的同 commit 约束**：清单记录正式目标和 RC commit；正式 tag 若已经存在，promote 会强制相同 commit。若还没创建，后续必须由维护者在该 commit 上创建并保护 tag。按“不改 release-assets.yml”的要求，本卡没有给既有正式发布门禁增加 RC commit 检查，因此不能宣称自动阻断所有未来错误 tag；仅新增 `-rc` tag 跳过正式 release 流程的 guard，避免白等 90 分钟。完整的远端强制约束需另行授权修改正式发布门禁或配置受保护 tag。
2. 原 `release-assets.yml` 的触发仍为 `v*`，RC tag 也会启动旧流程，但它拿到的 RC VERSION 不匹配正式 channel 包版本，不能到达上传；未绕过或取消既有门禁。正常正式 tag 仍需原门禁认可的同 SHA push/manual build（不把 workflow_call 偷换成旧门禁的成功记录）。
3. 原 channel `packages.yml` 仍能按既有行为构建并在 main 发布；RC 晋升应选择 promote，不应为同一版本重复触发旧 SDK 发布。删除旧路径超出本卡允许修改范围。
4. 已有同版本的历史包如果与 RC 字节不同，新路径故意拒绝晋升，不静默保留旧包冒充已晋升，也不覆盖。需要维护者按既有版本策略处理；本卡不升版。
5. 所有本地结果不代替真实 CI 与 H28K 人工验收。没有实际创建 prerelease/stable/正式 Release。
