## 根因分析与最小修复

### 信号接收、等待、消费与完成回调链路分析

旧版 `aether-proxy/src/lib/daemon.uc` 在 `run()` 中使用单个标量 `let signal = null` 记录所有控制信号，导致三类缺陷：

1. **异类待处理请求相互吞掉**：信号回调为 `else if (!ctx.stopping_requested && signal == null) { signal = kind; }`。当一个控制动作（如 `reload.run_live` 或等待 `monitor_daemon.busy`）在途期间，先后收到两种不同信号（例如 `SIGUSR2` 与 `SIGUSR1`），后到的信号看到 `signal != null` 被直接丢弃。
2. **忙时消费导致丢请求或重入**：
   - 当 `monitor_daemon.busy == true`（例如 `restart_xray` 在途）时收到 `SIGUSR1`，旧主循环仍立即清空 `signal = null` 并调用 `tick()`；`monitor.tick()` 见 `daemon.busy == true` 直接早退，导致 `SIGUSR1` 被静默吞掉。
   - 同样在 `monitor_daemon.busy == true` 时收到 `SIGUSR2`，旧主循环不检查 `busy` 即再次调用 `restart_xray()`，造成动作重入。
3. **异步完成回调未唤醒待处理控制请求**：`restart_xray` 的完成回调仅在 `ctx.stopping_requested` 时调用 `uloop.end()`；若有待处理的 `reload`/`tick`/`xray_restart`，主循环会停在 `uloop.run()` 等待下一次外部信号。此外 `wait_retry()` 与配置错误等待循环使用单标量 `signal`，若 `SIGUSR1`/`SIGUSR2` 先于 `SIGHUP` 到达，可能干扰或吞掉 `SIGHUP`。

### 最小修复（`aether-proxy/src/lib/daemon.uc`）

- 将单标量 `signal` 替换为独立待处理集合 `pending = { stop: false, reload: false, tick: false, xray_restart: false }`，新增内部辅助 `has_pending_control()` 与 `clear_non_stop_pending()`：
  - `SIGTERM`/`SIGINT`：仍先执行 `write_stopping(ctx)`，置 `pending.stop = true` 并调用 `clear_non_stop_pending()` 丢弃所有未开始的非停止请求，保持 T16.57 在途取消与停机优先语义。
  - `SIGHUP`/`SIGUSR1`/`SIGUSR2`：在 `!ctx.stopping_requested && !pending.stop` 时独立置 `pending[kind] = true`；同类型尚未消费时幂等合并，异类互不覆盖；首次记录 `pending.reload` 时保留 `reload_started_ms`。
  - `on_signal = () => pending.stop`：启动阶段（`wait_network`、`start_collector`、`bootstrap.resolve`、`xray_ready`、`stop_requested`）仅将 `stop` 视为停机取消，不把普通信号误当 `stop`。
- `run_monitor()` 主循环串行调度与忙时保留：
  - 循环顶部统一检查 `if (monitor_daemon?.busy)`：有待处理控制请求时以 `uloop.run(C.DAEMON_POLL_MS)` 有界等待完成（不忙等、不依赖下一次外部唤醒），无待处理请求时 `uloop.run()` 休眠。
  - 仅在 `!monitor_daemon?.busy` 时按 `reload` → `xray_restart` → `tick` 串行消费一个待处理请求，杜绝重入。
  - `restart_xray` 完成回调在 `!ctx.stopping_requested && !pending.stop` 时执行原有重启附带 `tick()`（**不清除 `pending.tick`**），并在 `ctx.stopping_requested || pending.stop || has_pending_control()` 时调用 `uloop.end()` 立即唤醒主循环消费后续待处理请求。
  - 保持 `failsafe` 阶段跳过 `SIGUSR2` 重启、`reload` 触发 `changed.stop` 时清空非停止待处理请求并停机。
- 启动失败待恢复路径（`result.step == 'config'` 与 `wait_retry()`）：仅响应 `stop` 和 `reload`，清理该阶段不合法的 `tick`/`xray_restart`，同时确保它们不会吞掉 `reload`。

## 隔离夹具与同步屏障设计

`tests/daemon/pending-requests.py` 复用 `tests/daemon/stop-during-xray-restart.py` 的真实 daemon + `--sys-root`/`--bin-dir` 隔离 stub 架构，不使用 `sleep` 猜时序，也不重复发信号碰运气：

- **信号已发送 vs daemon 已接收**：
  - 对触发在途动作的首个请求（`SIGUSR2` 或重启 Xray 的 `SIGHUP`），通过 Xray stub 的 `hold-xray-exit` / `xray-exiting` 文件屏障确认 daemon 已接收信号并进入在途执行（`T1`）。
  - 对忙时到达的后续控制信号，`send_and_wait_received()` 只发一次信号，并通过 `/proc/<pid>/status` 验证内核 `SigPnd`/`ShdPnd` 对应位已清零且 `voluntary_ctxt_switches` 递增，证明 daemon 已从 `epoll_wait` 唤醒并处理信号，而非停留在「`kill` 已调用」。
  - 对停机信号 `SIGTERM`，通过 `state.json` 原子发布 `state == "stopping"`（同时旧 Xray 仍被屏障扣留存活）证明 daemon 已接受停机（`T2`）。
- **对应动作已完成与排除假阳性**：
  - `SIGHUP`：以 `state.json.mode` 变更及 `events.jsonl` 的 `RELOAD_APPLIED` 证明配置实际应用；`mode` 变更不重启 Xray、不触发节点切换附带 tick。
  - `SIGUSR2`：以 `xray-launches.log` 的 `start`/`exited` 严格交替序列证明重启次数与无重入。
  - `SIGUSR1`：以 `curl-count` 观测检测调用次数；将 `s3`（`SIGUSR2` 忙时加发 `SIGUSR1`，`curl=3`）与正对照 `ctrl`（仅发 `SIGUSR2`，`curl=2`，仅含初始 1 次 + 重启附带 1 次）直接对照，且全程耗时 `< 15s`（远小于 30s 周期 `MONITOR_RUNNING_INTERVAL_MS`），彻底排除自动 tick 与重启附带 tick 的假阳性。
- 所有等待均有界（2s/5s/10s），`finally` 必然解除屏障并清理 daemon 进程组及全部子进程。

## 未覆盖边界

- 本任务按卡仅修 daemon 已收到信号后的待处理语义，不承诺内核层对多个重复标准 Unix 信号的逐个送达（内核本就会合并同号标准信号）。
- `monitor.tick()` 内部因异步恢复动作（如 `set_tier` 重启 DNS）置 `busy = true` 时的 `SIGUSR1` 延迟消费走与 `restart_xray` 相同的 `while (monitor_daemon?.busy) uloop.run(C.DAEMON_POLL_MS)` 分支；本套件直接用 `restart_xray` 与 `reload.run_live` 覆盖了忙时等待与唤醒，未单独构造 `monitor.uc` 异步 `set_tier` 屏障。
- `failsafe` 阶段跳过 `SIGUSR2` 及失败待恢复（`config` 错误 / `wait_retry`）仅接受 `stop`/`reload` 的代码路径已保留并同步迁移至 `pending`，其中 `SIGHUP` 失败重试由既有 `tests/daemon/run.sh`（`saved-set startup failure` + `SIGHUP retries immediately`）覆盖，未另增 `failsafe` 下的并发信号组合用例。
