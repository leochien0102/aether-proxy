## 实现边界与一致性

1. **保存的就是完整 read 结果**：`ok`、snapshot、data、paths、wan_dns、warnings，不从渲染结果反推，也不把 snapshot 塞给 build。monitor 只覆盖 node_ip、dns_tier、degraded_mode、restored。
2. **成功点**：启动完成最终发布、加载、状态写入及解锁后返回上下文；重载在全部动作和状态提交成功后统一返回/切换。无变化重载通过校验并成功更新必要元数据后也切换上下文；失败候选不进入 daemon。
3. **启动兼容性**：保留原有启动前检查及等待网络后刷新配置/WAN 观测的行为（既有 T9.23 回归要求）；从用于发布 chinadns 的那次 read 起固定上下文，后续 Xray/nft 和 monitor 不再重新读取。不是把启动早期的旧 WAN 观测误当已发布观测。
4. **数据缓存**：A/B 同路径 IP 文件原子替换后预热 B，A 的数组仍有效；nft 的最近一份排序缓存被 B 替换也只会重新排序 A，不从磁盘取得 B。paths 同代保留，B 的 data 优先路径不能取代 A 的 baseline 路径。
5. **降级/恢复**：仍完整执行既有事务、校验、集合导出、输出比对、动作及回滚；只是不能借此顺带应用新磁盘配置。无须另设旁路应用机制。
6. **外部路径内容**：初版只保存路径，复核发现同名源文件覆盖仍会混代；本轮修订按代冻结六份文件，详见文末「修订」。集合策略不变。
7. **缺失内部上下文**：明确失败，不回退到磁盘，不改变 snapshot。没有新增对外字段或事件码。

- 另写 `sources.json`，按固定顺序保存六项 `{ key, source, hash }`：原始来源路径和已捕获副本内容的 SHA-256。代标识是这个确定性 manifest（含结尾换行）的 SHA-256。测试独立用 Python hashlib 校验 manifest 中所有内容哈希和代名，且验证「相同内容、不同来源」会产生新代。
- 完整读取后、应用渲染前捕获六份文件的字节；先写入 0700 的 `.candidate`，对副本而非仍可变化的源文件求哈希，再原子改名为最终代目录。冻结后的 `paths` 才用于渲染、校验、子进程与动作；原始来源另存在 daemon 内部 `source_paths`。
- 源文件不存在时写真正的空文件；非 ENOENT 的读取错误仍失败，不当作空列表。启动的 boot 域名生成移到冻结之前，确保 chinadns 启动时就有本代的引导名单；既有 `write_boot_list` 计时字段保留。CLI check/render 不调用冻结函数，也不改变原始路径/输出。
- 相同来源且相同字节时，复用当前代及其 paths，不创建候选、不重写任何副本。仍走完整读取、渲染、输出比较与校验，不加「配置相同就跳过应用」快路径。测试比较六份文件及 manifest 的 inode/mtime，三次重载后全部不变。
- 用户重载统一在 `run()` 的事务边界清理：读取、渲染、校验、解析或动作/回滚失败，以及 stop 计划，都丢弃本次候选；与当前代相同的复用候选不能删除当前代。完整成功后先成对切换 snapshot/context，再清理除当前代外的目录。
- monitor 的降级/恢复仍复用现有上下文，不读取源文件、不重新冻结。启动成功后清理历史/崩溃残留；启动失败在停止部分启动的子进程之后清理全部候选和残留。启动拿不到锁时不清理，以免删除另一 daemon 的文件。
- 正常停止不提前删除成功代；下次启动成功保留新当前代并清理残留，启动失败清空。正常完成任意次数重载后，`applied/` 只有当前代，不会积累历史代。
