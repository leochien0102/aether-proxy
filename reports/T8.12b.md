## 实现与风格说明

- `probe now` 接受 `starting`、`running`、`degraded`、`failsafe`；其他状态及缺失文件不调用 ubus、不记事件。
- `signal` 由数值常量生成 JSON，服务名为 `aether-proxy`，不指定 `instance`，由 procd 向全部服务实例发信号。
- 在发送请求前取 `requested_at`，避免 daemon 在 ubus 返回前完成检测而使页面误判检测结果过旧。
- `sys.run` 默认已经记录命令名、退出码和 stderr，因此调用方不再重复记录 `CMD_FAILED`。
- 对比 reload 前的实时 IP，而不是启动时的 IP；在更新 monitor 快照和状态后执行检测，避免测到旧节点。
- 模块职责/设计出处和上述非显然决定均有注释；新增代码使用 tab，新增行按 tab=4 检查未超过 120 列；新增函数均少于 100 行。
- 既有 daemon 主循环本来超过 100 行，本卡在其现有 reload 分支内增加六行，不另行重构生命周期状态机，避免改变其他信号行为。
- 完成标准第 6 条：没有顺手改动无关既有行为；本卡对既有 reload 分支的改动有节点/IP 两条独立断言及变异测试，见下。

### 场景测试方法

- CLI 使用临时目录中的 ubus 脚本逐项记录 argv；既检查 `call/service/signal`，也解析请求 JSON 的服务名，并检查 JSON 原文中的 `signal` 是数值 `10` 而非字符串。用时间上下界检查 `requested_at`。
- daemon 使用真实主循环和子进程监督，先两次 SIGUSR1 预热并确认 `state=running`。新增第二节点的地址与旧节点相同，证明单独更换节点段名也必须检测；随后只改变当前节点 IP，证明 IP 条件独立有效。
- 立即检测断言限制为约 5 秒，短于既有非 running 的 10 秒和 running 的 30 秒周期，不靠定时器碰巧通过。检测后还核对 curl 调用恰好增加一次。
- 无关 reload 修改 `log_level`，先确认 Xray 校验替身调用数增加（reload 确实已经执行），再确认 curl 未增加。失败 reload 修改端口为 0，确认出现 `CONFIG_INVALID` 后再确认 curl 未增加。
- 所有验收测试在最终恢复的产品代码上重新执行；下面粘贴的是该轮完整输出。变异测试的失败是主动破坏实现的预期结果，不是最终验收失败。
