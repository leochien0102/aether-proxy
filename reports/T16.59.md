## 根因分析、实证事实与最小修复

### 1. 旧版失去独占的三条路径

沿真实入口 `aether-proxy/src/lib/daemon.uc:run()` 追踪：

1. **首次共享写入早于任何锁**：`run()` 在调用 `start_sequence()` 获取 `/var/lock/aether-proxy.lock` 之前，先写入 `state.json`（`state: "starting"`）与 `daemon.pid`（自身 PID）。即使首实例仍在启动期持着操作锁，竞争者在退出码 3 退出前已将首实例的 `state.json` 与 `daemon.pid` 覆写为竞争者自己的状态与已退出 PID（破坏 `cleanup --wait`）。
2. **短期操作锁不覆盖完整生命周期**：`start_sequence()` 在启动完成进入 `run_monitor()` 前（以及启动失败进入 `error`/退避等待前）释放 `C.LOCK_FILE`。此时同域再次启动第二个 daemon，不仅会覆写 `state.json` 与 `daemon.pid`，还能顺利拿到 `C.LOCK_FILE`，执行 `apply_cleanup()` 删除首实例的 nft 表/ip rule/dnsmasq 片段并拉起第二套子进程，两个 daemon 并发争抢数据面。
3. **并发首次启动时的目录创建竞争**：`sys.mkdir_p()` 先 `fs.stat` 再 `fs.mkdir`，当两个首次启动的 daemon 同时创建尚未存在的 `run_dir` 时，后一步 `fs.mkdir` 可能因 `EEXIST` 失败返回 `null`，导致竞争失败者以退出码 `1` 失败而非有序竞争锁后返回 `BUSY`（退出码 `3`）。

### 2. FD 继承与 ucode 绑定实证

在宿主固定 `tests/host/ucode` 上实测验证：

- **`O_CLOEXEC` 与子进程继承**：`sys.lock()` 使用 `fs.open(path, 'ae')`，`/proc/self/fdinfo/<fd>` 显示 `flags: 02102001`（含 `O_CLOEXEC`）；通过 `uloop.process()` 派生的子进程 `/proc/$$/fd` 中**不继承**该锁 FD。因此所有者被 `SIGKILL` 后，即使 `xray` / `chinadns-ng` 等子进程存活，内核仍立即释放 `flock`，不会阻挡后续实例接管。
- **`fs.error()` 绑定能力**：`tests/host/ucode` 的 `fs.error(true)` 与 `fs.error()` 均只返回错误文案（例如 `"Resource temporarily unavailable"`），不暴露数值 errno，且 `fs.open()` 失败时 `fs.error()` 常为 `null`。因此不依赖错误文案猜 errno，改为沿用 `sys.lock()` 已有的**阶段区分**：
  - `mkdir_p` 或 `fs.open(path, 'ae')` 失败（`sys.lock_retryable() == false`）：确认为**建锁失败**，记 `START_FAILED {step: "instance_lock", detail}`，向 stderr 输出诊断，以退出码 `1` 拒绝启动，绝不冒充 `BUSY`。
  - 有效打开句柄上 `fp.lock('xn')` 失败（`sys.lock_retryable() == true`）：映射为竞争忙，记 `BUSY {holder: "daemon"}`，向 stderr 输出诊断，以退出码 `3` 快速退出。

### 3. 最小修复

- `const.uc`：新增 `DAEMON_LOCK_FILE = 'daemon.lock'`。
- `sys.uc`：`mkdir_p()` 在 `fs.mkdir(cur)` 失败后先保留原 `fs_err()`，再 `fs.stat(cur)` 复核；若 `existing?.type == 'directory'` 则视为并发已建好继续，否则原样返回原 `mkdir` 错误。
- `daemon.uc`：
  - 在 `run()` 解析参数与 `setup_log(ctx)` 之后、首次读写 `state.json` / `daemon.pid` 之前，对 `${run_dir(ctx)}/${C.DAEMON_LOCK_FILE}` 获取非阻塞排他 `flock`（自动尊重 `--sys-root` 与 `--run-dir`，不落宿主真实系统路径）。
  - 全程持有至 `run()` 全部退出路径（含早期失败、正常停机 `shutdown`、`raw_collector` 停止与 `uloop.done()` 之后）再通过 `release_instance_lock()` 显式 `lock('u')` 并 `close()`；**任何清理路径都不 `unlink` 锁文件**，确保同域竞争者始终在同一 inode 上原子互斥。
  - 保留 `start_sequence()` 对短期操作锁 `C.LOCK_FILE` 的原有获取与释放时机，以及 T16.58 的全部信号处理语义。

## 隔离夹具设计（`tests/daemon/instance-owner.py`）

- 复用 `tests/stubs/daemon-bin` 与 `--sys-root`/`--bin-dir` 隔离结构，仅在临时目录的 `nft` stub 副本加入 `hold-nft-check` / `nft-check-entered` 文件屏障，在 `xray` stub 副本记录 `xray-launches.log`，不修改生产代码。
- 竞争窗口内通过 `SnapshotWatcher` 后台线程每 2ms 采样 `daemon.pid` 与 `state.json`，记录全窗口出现过的 PID、状态序列与 `started_at`，并校验 `calls.log` 中的变更类调用（显式排除正常 monitor 只读探针 `nft list table` / `nft -j list counters` 与 `curl`，且通过 `started_at` 不变与无 `starting` 状态排除正常 monitor 更新快照造成的误判）。
- 所有等待均有界，`finally` 解除屏障并回收全部 daemon 与子进程。

## 未覆盖边界

- **非竞争类 `flock()` 内核错误**：因 ucode `fs` 绑定不暴露数值 errno，若特殊文件系统（如不支持 `flock` 的网络挂载或内存耗尽触发 `ENOLCK`/`ENOMEM`）在有效文件句柄上使 `fp.lock('xn')` 失败，当前按阶段映射仍返回退出码 `3`（`BUSY`）并在 stderr 保留底层错误文本；本地 tmpfs / `/var/run` 上建锁失败（目录/权限/路径类型错误）均已准确映射为退出码 `1`。
- **真机 / procd 实测与异构 `cleanup`/`reload` 操作锁**：本卡未在真机运行，也未改动 M1/M2 涉及的 `cleanup`/`reload` 操作锁范围。
