## 实现

### Manifest / builder

文件：`tools/channel/build.py`、`tools/channel/test_build.py`。

- 增加 `--compatibility <JSON>` 输入，格式为完整 compatibility 对象；省略时保留上一份清单的 compatibility，包括仅数据发布。
- `compatibility.aether-proxy.steps` 每步包含 `version`、`min_from`、`assets`、非空 `reason`。
- 同级 `required_steps` 为独立审核、冻结的必经版本列表，不从 steps 自动生成。校验版本序列与其完全相等，防止删除中间步后重接 `min_from` 掩盖断档。它不能检测维护者同时修改 itinerary 和 steps；两者需独立审核。
- 校验严格递增、精确前驱衔接、末步精确匹配 current、架构/格式/安全文件名/hash/正整数 size。存在但为 null/空对象的 compatibility 不能静默恢复直升。
- 新引入的历史包从 compatibility JSON 同目录读取，验 hash/size 后复制；已发布引用保持原元数据。旧链未扩展到新 target 时明确失败。

### 设备端 / CLI

文件：`aether-proxy/src/lib/update.uc`。

- check 只暴露下一步，新增 `bridge_required`、`next_step.version/reason`、`steps_remaining`。三个应用入口都指向相同的下一步后端资产，不暴露 target 页面资产。
- 无效链返回条目级 `BRIDGE_UNAVAILABLE`、具体步骤/架构/衔接等原因，`newer=false`、`asset=null`；独立 Xray 和数据流程不受影响。
- 沿用现有兼容 CLI `update package <包>`，没有新增替代旧命令的入口。每次安装重新取签名清单并计算链，后端、页面、翻译三个 CLI 入口都只能安装下一步后端。
- 成功返回 `BRIDGE_INSTALLED`；一次调用只安装一个步骤，不循环推进。到达 target 后正常分组更新可以补齐页面/翻译。
- 缺资产、下载/hash/size 失败均不能回落安装 target；下载完整性失败返回 `BRIDGE_UNAVAILABLE`。安装/健康验证失败保留既有失败码；本地空间/文件系统失败保留原错误码。
- 自动恢复只选精确匹配更新前版本的 bridge 或 previous，不把 target 当恢复包；无匹配恢复资产则明确失败。`--previous` 仍仅允许 `aether-xray`。
- 无 compatibility 时不增加包管理器查询，保持已有直升、分组、自动恢复行为。

### Stable 资产保留：外部仓库部署前置条件

实际 publisher 位于独立 channel 仓库，不能通过本应用分支的提交直接部署。新增：

`tools/channel/publish-bridge-assets.patch`

该补丁扩展 channel `scripts/publish.sh` 的共用 URL 集合，使上传、存在性检查、过期删除都包含 compatibility steps 资产，保留超出 current/previous 的 bridge。回归测试对真实 channel publisher 的**临时副本**应用补丁并执行离线验证，也验证旧无链清单行为。

**实际发布 bridge 清单前必须先部署此补丁，并接入 `--compatibility` 输入及桥接资产供应。仅部署设备端或 builder 不会自动修复外部旧 publisher。** 本任务没有修改 `/workspace/openwrt/aether-proxy-channel` 工作区，也没有实际运行发布。
