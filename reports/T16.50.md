# T16.50 配额与流量落盘并发锁

## 范围与实现

- 工作树：`/workspace/openwrt/aether-proxy-wt/T16.50`；分支 `feat/t16.50-usage-lock`；基线 `9f9658842ceb78ff1a51bfab6176b8e03401b2d7`。
- `usage.uc` 统一事务：`sys.lock(path + '.lock')` → 读取最新文档 → 合并 → `sys.write_atomic()` → close。锁文件稳定、不删除，不锁被 rename 替换的账本 inode，不复用 daemon 操作锁；路径随测试 sysroot 隔离。
- 锁获取非阻塞，等待上限为零；锁忙明确失败，由命令调用者重试或下次 flush 重试。正常结果、读取失败、写入失败和捕获异常均释放持锁句柄。
- `monitor.flush_usage()` 改为调用 `usage.flush()`；磁盘、缓存、完成日和本日逐字段取最大值，只有成功替换才推进 `usage_days`。失败不修改完成日累积。quota set/clear 及低层 `usage.write()` 也走同一事务，不接受调用者缓存的 quota 文档。
- 非 ENOENT 读取失败、解析失败一律拒绝覆盖；只有确实不存在时允许初始化。只读查询不取锁，仍通过原子替换只看到旧/新完整文档。
- 格式、0600、90 日窗口、8 MiB 门槛、采样节奏、停用/停止入口不变；普通采样没有新增账本 IO/取锁。
- 修改限卡内白名单；另经用户明确许可修改 `tests/daemon/usage-persist.py` 的 Scenario 3 及说明：旧“覆盖损坏账本”断言与本卡保护行为冲突。其他 daemon 用例和断言未改，没有跳过测试。

## 确定性同步与读回

入口：`python3 tests/monitor/usage-lock.py`，已接入 `tests/monitor/run.sh`。

每例两个独立 ucode 进程，执行真实 `monitor.flush_usage()` 与 `usage.set_quota()`。仅在一次性私有模块副本设置同步点（产品代码没有测试钩子）：

1. `after-read`：第一次写者读完账本，stdout 通知父进程后阻塞 stdin；证明取锁早于读取。
2. `before-write`：第一次写者完成合并、进入原 `write_atomic` 前通知并阻塞；证明锁覆盖到原子替换。
3. 父进程收到通知后启动第二写者，读其明确失败结果，此时逐字节核对原文件不变；通过管道释放第一写者，等其完成，再向第二写者发送 `retry`。第二次尝试在原进程成功。
4. 精确比较整个最终 JSON（含日期键集合、quota、四项累计、updated_at、未知字段和文件权限），不是仅检查 JSON 可解析。

没有固定 sleep、随机循环或全局重试。`select`/进程 wait 的 10 秒上限仅防止死锁，不决定执行顺序。

固定数据：初始 `2026-11-17` 的 `(tx,rx,observed,healthy)=(100,20,30,10)`，旧 quota `(50000000000,111)`，旧 `updated_at=123`。新本日累计 `(150,40,45,20)`；跨日时完成日输入 `(130,15,35,8)`，逐字段合并得到 `(130,20,35,10)`。固定写入时间 `1795000000`。

下列每行在 **after-read 和 before-write 两个同步点各执行一次**（16 例全通过）：

| 操作 | 首次持锁者 | 日期 | 最终 quota `(bytes,set_at)` | 最终 days：日期 → `(tx,rx,observed,healthy)` |
|---|---|---|---|---|
| set | quota | 同日 | `(200000000000,1795000000)` | 11-17 → `(150,40,45,20)` |
| set | flush | 同日 | `(200000000000,1795000000)` | 11-17 → `(150,40,45,20)` |
| clear | quota | 同日 | `(null,null)` | 11-17 → `(150,40,45,20)` |
| clear | flush | 同日 | `(null,null)` | 11-17 → `(150,40,45,20)` |
| set | quota | 跨日 | `(200000000000,1795000000)` | 11-17 → `(130,20,35,10)`；11-18 → `(150,40,45,20)` |
| set | flush | 跨日 | `(200000000000,1795000000)` | 11-17 → `(130,20,35,10)`；11-18 → `(150,40,45,20)` |
| clear | quota | 跨日 | `(null,null)` | 11-17 → `(130,20,35,10)`；11-18 → `(150,40,45,20)` |
| clear | flush | 跨日 | `(null,null)` | 11-17 → `(130,20,35,10)`；11-18 → `(150,40,45,20)` |

日期均为 2026 年。所有最终文档 `schema=1`、`updated_at=1795000000`、`extension={"keep":true}`、mode 0600。

## 基线反证

从 `git archive 9f965884 aether-proxy/src/lib` 提取到本工作树内测试临时目录，使用相同 Suite、相同同步点，不修改工作树生产代码。分别调用 `Suite.race('set', first, False, 'before-write')`，`first` 取 quota/flush，均捕获预期的 `LOST UPDATE` 精确差异：

- quota 先读后停：独立 flush 成功写入 `(150,40,45,20)`，quota 随后覆盖，最终回退到 `(100,20,30,10)`，`updated_at` 回退到 123。
- flush 先读后停：独立 quota 成功设为 `(200000000000,1795000000)`，flush 随后覆盖，最终 quota 回退到 `(50000000000,111)`。

测试也提供 `--source <基线源码目录> --race-only`，直接执行会在首例以 `LOST UPDATE` 失败，不依赖新 API 缺失来制造红灯。

## 故障与恢复证据

另 16 例：4 类故障 ×（flush 同日、flush 跨日、quota、低层 write）。

| 故障 | 注入/解除方式 | 失败时断言 | 同进程重试结果 |
|---|---|---|---|
| 锁忙 | 独立 holder 取得同一 `.lock`，管道通知；完成断言后显式 close | 原字节完整；quota/write `ok=false`；flush 水位不前移 | 获取同锁成功，完整精确 JSON 匹配 |
| 写失败 | 在私有包装中创建 `usage.json.tmp.<实际写者PID>` 目录，继续执行原 `write_atomic`，触发真实 `wxe` open 失败；随后 rmdir | 原字节完整、水位不前移；待写完成日逐字段不变 | 原进程重新取锁，真实原子写入成功 |
| 读失败 | 私有 load 的显式失败标记；随后撤除 | 旧 quota/文档没有被空文档覆盖，返回失败，水位/完成日不变 | 重新读取最新文档并成功落盘 |
| 损坏 JSON | 截断旧 JSON；随后恢复原合法字节 | 损坏原字节完整，拒绝覆盖，水位/完成日不变 | 成功落盘，配额和累计均精确匹配 |

flush 失败时 `usage_days` 精确保持初始历史，跨日 `usage.days` 精确保持 `{2026-11-17:(130,15,35,8)}`。解除故障后最终同日/跨日累计与上表相同，证明没有丢弃待写完成日。quota 重试保留旧历史和 `updated_at=123`，只更新 quota；所有失败后原进程都能再成功取锁，未泄漏锁。

实际汇总：`PASS T16.50 deterministic usage lock suite: 32 cases`。

CLI 另做实测：Python holder 用 `fcntl.flock` 持有测试根下同一 sidecar，独立 CLI 运行 `stats quota set 200G` / `clear`，均 exit 1、单 JSON `{"ok":false,"code":"FS_FAILED",...}`，旧文件逐字节不变。释放锁后两命令均 exit 0，先读回 quota bytes=200000000000，再读回 `(null,null)`，历史保持原样。损坏账本上的 set 同样 exit 1 且损坏原字节不变。

额外 daemon Scenario 3：保留 `daemon exits cleanly on TERM` 和恰一次 warn 断言；停止后 `'{not json'` 逐字节不变。显式修复账本（quota `(100000000000,17)`、历史 `2026-01-01:(11,22,30,20)`），给 tmpfs 恢复入口一个已知本日累计 `(150,40,45,20)`，再次正常启动/停止。精确断言本日落盘等于该累计，原 quota 和历史保持不变。该集成用例不替代上述并发测试。
