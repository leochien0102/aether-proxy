- 原始 `render xray` / `render xray --json` 是含密配置导出，不是脱敏诊断接口，保持既有接口并在配置文档明确提醒。实际渲染文件沿用 `sys.write_atomic()` 的 `0600`；日志 `access: 'none'` 不变。

## 离线真实 Xray 验收

新增 `tests/explicit-proxy/{acceptance.py,render.uc,README.md}`。测试经真实 UCI → `config.load()` → 生产渲染器，并与真实 CLI render 逐字节比较；不手拼被测主配置、不删透明入站以绕过权限。仅测试上游使用独立的本地 Xray SOCKS 服务，目标为本地 HTTP 和使用临时自签名证书的 TLS HTTP 服务。没有公网依赖。

每个版本均验证：

1. 字段省略、显式双关、仅 SOCKS、仅 HTTP、双开：完整配置均通过 `xray run -test` 并实际启动；双关与旧渲染完全相同。
2. 读取被测 Xray 的实际 `/proc/<pid>/fd` 和 TCP listener，启用端口只有 `127.0.0.1`，关闭端口不存在；诊断 31081 未改。
3. 两种入站的正确认证分别经上游访问 HTTP 和 TLS 目标成功：SOCKS5 / SOCKS5 到 TLS、HTTP 转发 / HTTP CONNECT 到 TLS。不是 TLS 到代理。
4. 无认证、错误用户名、错误密码请求均失败，HTTP/TLS 目标 TCP 接受计数均不增加。
5. 停上游后所有有效认证请求均失败，目标 TCP 零新增命中；直连控制请求仍能成功，证明不是目标宕机造成的假阳性。
6. 默认宽松 `umask 000` 下生产原子写入器仍生成 `0600` 渲染文件；CLI render 不意外创建运行日志目录。临时配置/证书和进程均清理。

完整主配置含现有 TPROXY 入站，因此测试需要相应权限且 31080–31083 空闲；未触碰宿主防火墙。
