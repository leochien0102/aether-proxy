## 根因与核对结论

### 代码核对（`daemon.uc` 与 `sys.lock`）

1. **`sys.lock()` 打开与继承模式**（`aether-proxy/src/lib/sys.uc:263-290`）：
   - 使用 `fs.open(path, 'ae')`（含 `O_CLOEXEC`）并以 `fp.lock('xn')` 获取非阻塞独占 `flock`。
   - 宿主机 `tests/host/ucode` 实测 `/proc/self/fdinfo/<fd>` 显示 `flags: 02102001`（包含 `O_CLOEXEC = 02000000`），因此 `uloop.process` 经 `exec` 启动的子进程（`xray`、`chinadns-ng` 等）不会继承操作锁 fd。
2. **失败出口差异**（`aether-proxy/src/lib/daemon.uc:869-890`）：
   - `start_sequence()` 中其余所有失败出口均显式调用了 `locked.close()`，成功路径在返回前显式调用 `locked.lock('u')` 与 `locked.close()`。
   - 唯独组件就绪后最后一次 `write_state(ctx, initial_state)` 失败分支（原第 872–873 行）直接 `return { ok: false, code: 1, step: 'state', detail: state_result.detail, children };`，未显式解锁或关闭 `locked`。
3. **区分“缺少显式释放”与“永久自锁”**：
   - 在当前 pinned `ucode` 构建上，局部变量 `locked`（及捕获它的局部闭包 `interrupted`）随 `start_sequence()` 返回离开作用域，经引用计数隐式析构并关闭底层 fd；叠加 `O_CLOEXEC` 阻止子进程继承，**基线在真实内核 `flock` 层面并不会永久自锁为 `lock_busy`（exit 3）**——在 daemon 仍存活于 `START_RETRY` 退避等待期间，独立持有者即可因隐式关闭重新取得 `C.LOCK_FILE`。
   - 但该出口确实**缺少显式解锁与关闭**，把操作锁释放契约完全寄托于运行时隐式析构时机，与同函数成功路径及其他失败出口不一致。

### 改动说明

1. **`aether-proxy/src/lib/daemon.uc`**：
   - 仅修改 `!state_result.ok` 失败出口，在把原错误返回给调用者前显式解锁并关闭本次操作锁：
     ```javascript
     if (!state_result.ok) {
         locked.lock('u');
         locked.close();
         return { ok: false, code: 1, step: 'state', detail: state_result.detail, children };
     }
     ```
   - 保留原 `ok`/`code`/`step`/`detail`/`children`，不触碰 `instance_lock`（`daemon.lock`），不改变 `save_start_failure()` -> `shutdown()` 子进程与数据面清理顺序。
2. **`tests/daemon/startup-state-lock.py` 与 `tests/daemon/run.sh`**：
   - 新增独立回归 `tests/daemon/startup-state-lock.py` 并接入 `tests/daemon/run.sh`。
   - 通过隔离夹具在 `/etc/init.d/dnsmasq` 首次安装回调（此时 `xray` 与 `chinadns-ng` 均已就绪运行、操作锁与实例锁均处于持有态）将 `$RUN_DIR/state.json` 替换为同名目录以稳定触发 `EISDIR`，使启动精确在最后一次 `initial_state` 写入处失败；在回滚 `dnsmasq_remove` 时移除该目录以便 `save_start_failure` 写入 `error` 状态并进入 `START_RETRY` 等待。
   - 以 `events.jsonl` 出现 `START_RETRY` 为确定性同步点（无 `sleep` 猜时序），在 daemon 进程**尚未退出**时同时验证：
     - `START_FAILED` 的 `step == "state"`、`state.json` 为 `state: "error", failed_step: "state"`、未发 `SERVICE_STARTED`；
     - 已启动的 `xray` 与 `chinadns-ng` 子进程均按原回滚路径清理退出且无残留 pid 文件；
     - 独立持有者（`fcntl.flock(LOCK_EX | LOCK_NB)`）可立即取得 `C.LOCK_FILE`；
     - `daemon.lock` 仍被存活 daemon 持有（独立 `flock` 返回 `BlockingIOError`，并发第二实例退出码为 `3`），直到 `SIGTERM` 退出后才释放；
     - 通过仅包裹临时副本 `sys.lock()`（不改 `daemon.uc` 源码）的跟踪观测，验证 `C.LOCK_FILE` 在该失败出口确实显式调用了 `lock('u')` 与 `close()`，而 `daemon.lock` 在 daemon 存活期间未被解锁或关闭。
   - 保留正常启动与实例锁对照（真实入口与跟踪副本各一组）。

## 未验证边界

1. **实机 OpenWrt 环境**：本卡未操作路由器设备，所有验证均在宿主机隔离夹具（`tests/host/ucode` + `tests/stubs/daemon-bin`）下完成。
2. **`locked.lock('u')` 本身返回失败的极端内核场景**：失败出口已处于 `state` 错误路径，为保持原失败 `step`/`code`/`detail` 不被改写，依次执行 `locked.lock('u'); locked.close();` 后返回原 `state` 错误；即使 `flock(LOCK_UN)` 异常，随后的 `locked.close()` 仍会关闭该 fd。
