## 支持的输入类型、非法值边界与 `path`/`type` 决策

仅在 VMess base64 JSON 且 `net == "grpc"` 时处理以下显式字段；非 gRPC VMess（如 `tcp`/`raw`/`ws`/`xhttp`/`httpupgrade`）完全不受影响，即使携带 `serviceName`/`multiMode` 也不写入节点字段：

1. **`serviceName` → `node.service_name`**：
   - 支持：非空 JSON 字符串（原样保留为 `node.service_name`）。
   - 视为缺省（省略字段）：键缺失、`null`、空字符串 `""`。
   - 拒绝（`skipped('invalid_value')`）：非字符串类型（如布尔 `true`、整数 `123`、数组 `[]`、对象 `{}`），避免隐式转字符串污染配置。
2. **`multiMode` → `node.grpc_multi_mode`**：
   - 支持（显式真 → `'1'`）：JSON 布尔 `true`、小写字符串 `"true"`、字符串 `"1"`。
   - 支持（显式假 → `'0'`）：JSON 布尔 `false`、小写字符串 `"false"`、字符串 `"0"`。
   - 视为缺省（省略字段）：键缺失、`null`、空字符串 `""`（兼容 v2rayN 模板将未填可选字段序列化为 `""` 的习惯）。
   - 拒绝（`skipped('invalid_value')`）：任何其他非空字符串（如 `"yes"`、`"no"`、`"on"`、`"multi"`、`"gun"`、`"TRUE"`、`"FALSE"`、`"bogus"`、`"2"`）及非布尔/非字符串类型（如整数 `1`/`0`、数组 `[]`、对象 `{}`）。采用严格相等 `===` 判定，绝不因非空字符串为真值而误判为 `true`。
3. **为何不对 `path` / `type` 做 gRPC 重载映射**：
   - 本仓库当前文档（`docs/06-nodes-subscription.md`）仅将 VMess JSON 的 `path` 定义为 `path`、`type` 定义为 `header_type`，未定义任何客户端特定的 `path → serviceName` 或 `type (gun/multi) → multiMode` 重载规则。
   - 反例 1：大量 v2rayN JSON 模板无论传输方式如何都会输出占位字段 `"type": "none"`；若把 `type` 解释为 gRPC 模式，会把合法的 `"type": "none"` 误判为非法值或错误覆盖。
   - 反例 2：若把 `path` 启发式搬运到 `service_name`，还面临前导 `/` 是否剥离、原 `path` 字段保留还是清空等歧义，而 `identity.uc` 以 `tdisc = path + "|" + host + "|" + service_name` 计算强/弱键，猜测搬运会破坏既有节点去重与身份稳定性。
   - 因此本卡严格遵守“不猜测客户端方言”，只映射显式 `serviceName` 与 `multiMode`，并通过单测锁定 `net=grpc` 下 `path: "/legacy"` + `type: "none"` 仍按原字段保留而不被猜测改写。

## 改动说明

1. **`aether-proxy/src/lib/uri.uc`**：
   - 新增 `parse_vmess_bool(value)`，仅用 `===` 精确匹配 `true`/`'true'`/`'1'` → `'1'`、`false`/`'false'`/`'0'` → `'0'`，其余返回 `null`。
   - 在 `parse_vmess()` 中仅当 `net == 'grpc'` 时校验并映射 `data.serviceName` → `node.service_name`、`data.multiMode` → `node.grpc_multi_mode`；非法类型或取值返回 `skipped('invalid_value')`。
2. **`tests/unit/uri.uc`**：
   - 新增 31 条脱敏用例：
     - `multiMode` 三态与全部支持输入类型（`true`/`"true"`/`"1"`、`false`/`"false"`/`"0"`、缺省/`null`/`""`）及 `serviceName` 空值/缺失对照；
     - 17 条非法值拒绝用例（`"yes"`、`"no"`、`"on"`、`"multi"`、`"gun"`、`"TRUE"`、`"FALSE"`、`"bogus"`、`"2"`、整数 `1`/`0`、数组/对象，以及非字符串 `serviceName`），确保不会因字符串非空转真；
     - 非 gRPC VMess（`net=ws`）忽略 `serviceName`/`multiMode`，以及 `net=grpc` 下 `path`/`type` 不被猜测改写。
3. **`tests/node/parse.py`**：
   - 自动将上述全部 31 条用例走真实 `aether-proxy node parse` 与 `aether-proxy node import` 入口做落盘一致性校验；
   - 新增 10 条端到端链路断言：对 `multiMode=true`、`multiMode=false`、`multiMode` 缺省三组脱敏样本依次执行 `aether-proxy node import` → 读取落盘 UCI → `config.load()` 归一化快照 → `render/outbound.uc` `build_outbound()`，逐层验证 `service_name`/`serviceName` 与三态 `grpc_multi_mode`/`multiMode`；另验证不同 `serviceName` 的 VMess gRPC 节点在 `node import` 中不碰撞去重。

## 未验证边界

1. **客户端重载方言未支持**：部分客户端将 VMess gRPC 的服务名写入 `path`、将 `gun`/`multi` 写入 `type`；因缺乏统一格式契约且与默认 `type: "none"` 及 `identity.uc` 强键存在冲突风险，本卡明确不猜测映射，仅处理显式 `serviceName` 与 `multiMode`。
2. **订阅更新路径下的 VMess gRPC 变更热更新**：已在代码层面核对 `sub.uc` 的 `NODE_PROTOCOL_FIELDS` 与 `protocol_value('grpc_multi_mode', ...)` 支持三态比较与 `delete_option`，并跑通既有 `tests/sub/run.sh`（含 VLESS gRPC `multiMode` 回归），但未新增专门的 VMess gRPC 订阅夹具做多次轮换演练。
3. **实机与真实 Xray 运行时连通性**：本卡未触碰路由器设备，也未用真实 VMess+gRPC 服务端做端到端拨号验证；出站配置仅通过 `render/outbound.uc` 结构断言与 `tests/ci/xray.sh` 既有 `xray -test` 校验。
