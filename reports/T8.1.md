## 偏差与待定
- **`service` 后台启动失败的处理**：docs/10 只规定「放到后台执行后立即返回 `{"ok":true,"action":…}`」，未定义 `sh -c` 包装层本身失败的情形。按 README 规则 1/2（保守、错误可见），此时返回 `{"ok":false,"code":"CMD_FAILED","detail":"exit <rc>: …"}`（`sys.run` 同时以 `CMD_FAILED` 记 syslog）；动作真正的结果仍由前端轮询 `status` 得知。已在代码注释说明。
- **事件等级枚举**：等级表（error/warn/notice/info/debug，docs/09）只以 `RANK` 的形式存在于 `lib/log.uc` 内部，`aetherproxy.const` 未导出；本卡不准改 `aether-proxy/`，插件内维护了一份副本并标注 `TODO(design): the event level enum (docs/09) lives only as lib/log.uc's RANK table and is not exported by aetherproxy.const; this card may not change aether-proxy/, so the list is kept in sync by hand.` 建议后续卡把 `EVENT_LEVELS`（或 `RANK`）从 lib 导出，插件改为导入。
- **超时与截断常量**：`check` 30s / 其余 10s / stderr 截 512 字节是 docs/10 的值，但 `const.uc` 同样不在本卡允许改动范围内，故在插件顶部以命名常量定义（`CHECK_TIMEOUT_SECS`、`DEFAULT_TIMEOUT_SECS`、`STDERR_FORWARD_BYTES`），未散落字面量。
- **场景 4 的 check 30s 绝对值未实测**：让替身睡 31s 验证 check 的 30s 上限代价过高（单用例 >30s）。改为用「替身睡 11s 被 check 正常应答（10 < t < 29）」证明 check 的超时预算大于默认的 10s；30s 这个精确值目前只能靠代码与设计文档核对。若需要实测，建议放进真机验收（T8.13）。
- **tests/review.sh 的 WARN 解释**：提交后的运行预期只有一条 WARN——`.github/workflows/test.yml changed (shared infrastructure; explain in the report)`，这是任务卡「允许改动」明确要求的（增加运行 `tests/rpcd/run.sh` 的 CI 步骤）。
- **测试实现备注**：`deep_eq` 为测试内自写的类型严格递归比较（ucode 无内置深比较）；插件文件用 `loadstring`（编译源码取返回值）加载，与 rpcd 的加载方式一致（文件无 `export`，`import` 得到的是空命名空间，docs/12 语法限制 3）。
