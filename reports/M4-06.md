# M4-06 channel 管道接入 aether-dns

## 起因

1.0.0 把 `aether-proxy` 的 DNS 硬依赖从 `+chinadns-ng` 换成虚拟包 `+dns-engine`，需要
`aether-dns 1.0.0-r1` 出现在 `channel-stable` 清单里，否则 0.7.0 设备升级时事务无法安装引擎。
按 A 方案，`aether-dns` 由 DNS 仓库构建，channel 只做下载、校验、签名、发布。

## 改动

### aether-proxy

- `tools/channel/build.py`：`PACKAGE_NAMES` 增加 `aether-dns`（注释说明它由 DNS 仓库构建，
  本管道只校验与发布）；`ARCH_ALL` 不变（架构相关）。
- `tools/channel/test_build.py`：新增三条用例——prebuilt 双格式收集、缺 apk 必须报错、
  `aether-dns` 属架构相关包。
- `docs/08-updates.md`：通道段说明 aether-dns 的构建归属、pin 校验与 stage 位置。

### aether-proxy-channel（所有者执行，未由实现者推送）

- 新增 `AETHER_DNS_RELEASE`（repo/tag/version）与 `AETHER_DNS_SHA256SUMS`（四个资产）。
- `packages.yml` 的 publish 作业在 `Build usign` 之前新增 `Stage prebuilt aether-dns packages`：
  `gh release download` → `sha256sum -c` → 复制到 `packages/<arch>/channel/` → 校验 ipk 控制文件的
  `Provides: dns-engine` 与 apk 的 ADB 魔数。任何一步失败即中止发布。

## 验证

1. `python3 -m unittest tools.channel.test_build -q` → **27 tests OK**（含新增 3 条）。
2. 本地模拟 staging：四个资产 sha256 全部 OK；stage 后目录为 `packages/<arch>/channel/`；
   ipk 控制文件含 `Provides: dns-engine`；apk 魔数为 `ADB`。
3. 用真实 staged 目录跑 `build.collect_packages()`：得到 `aether-dns 1.0.0-r1`，
   两个架构、两种格式齐全、size 与 Release 一致（ipk 840433/832482，apk 838634/826583），`ignored` 为空。
4. `bash tests/review.sh` → 0 FAIL，1 WARN（docs 变更，本卡授权）。

## 边界与已知风险

- channel 侧 workflow 只能在下次 `AETHER_PROXY_REF` 推送时真正执行；本次用本地等价脚本验证了每一步命令。
- 不在 publish 前安装包做运行验证（channel 无 smoke 环境）；改为校验包元数据，真实安装验证放到
  1.0.0 的设备窗口。
- 不改 `publish.sh`：`build_to_dir()` 会把 staged 资产一并写出，清单引用即上传。

## 不做

- 不改 aether-proxy 的依赖与版本（M4-05）。
- 不改 DNS 仓库、不触发真实发布。
