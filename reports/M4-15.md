## 一次构建的时序（文字）

```text
应用 main push / 显式 workflow_dispatch（commit S）
  → build.yml：4 组 packages，上传 packages-<SDK>-<arch>，保留 90 天
  → 6 组 smoke 下载上述同一批产物并成功 → 整个 build 运行 success
维护者在 S 创建 RC tag
  → release-candidate：tag^{commit}=S
  → 分页选择 S 上最新成功 push/dispatch 门禁运行 R
  → 校验四个 artifact 的 run/SHA/名称/有效期，按 IDs 从 R 下载
  → 校验 20 包 → 原样复制 → rc-manifest.json + SHA256SUMS → prerelease
人工验收这批字节
  → channel promote：只下载/校验/签名/发布，不编包
  → 正式 tag 指向 S → release-assets 从 channel 复制与校验，不编包
```

“每个 commit 一次构建”指常规成功链路不在 RC 或 promote 再构建；手动恢复超期产物是明确例外，不宣称与原批次字节相同。

## 回退条件与保留期处理

- 无成功运行、过期/删除/空产物、矩阵不全、SHA 不符均失败；API 错误也失败，不自动重建、不取其他 commit、不拼接不同运行的四组包。
- 仅从最新成功运行取整组产物；若这组有问题不悄悄退回更老运行。先显式恢复门禁，再重跑 RC。
- upload-artifact 显式 90 天；仓库/组织策略必须允许 ≥90 天，GitHub 实际有效期为准，不假定旧产物自动延长。
- 文档路径过滤导致无门禁、或产物超期时，维护者显式 dispatch build.yml 到 tag 的同一 SHA，等待四组构建和六组 smoke 全绿，再重跑 RC。确切 SHA 无可 dispatch 的 ref 时先由维护者提供固定 ref；不自动在最新 main 编译。超期重建须重新验收。
- channel packages 仅是显式输入固定 ref 的人工回退，不是 RC 内建 fallback。已有同版本不同字节不得覆盖，必须遵守版本策略；本卡不修改 channel workflow。
