# T16.108 — 本机显式入站重载就绪验证

## 范围与结论

- 工作树：`/workspace/openwrt/aether-proxy-wt/T16.108`；基线：`8d7a7efcabd7aebc68ac4157a481eb8be5f54979`。
- 基线**不满足**本卡：生产渲染已生成独立的 `explicit-socks` / `explicit-http`，但 `xray_ready.requirements()` 只收集 TPROXY 与被 DNS 引用的 tunnel，故显式端口缺失不阻止就绪成功。
- 最小修复仅在 `aether-proxy/src/lib/xray_ready.uc`：从已发布的 `current/xray.json` 收集存在的显式入站，验证独立标签唯一、对应协议、合法整数端口及固定 `127.0.0.1`，要求 TCP LISTEN。沿用既有 child PID/starttime、FD socket inode、共享五秒预算、信号取消及事务回滚；显式入站要求精确 loopback，不接受本代持有的 wildcard 监听冒充。
- 不修改 daemon/reload/monitor 调用接口：首次启动、直接重启、重载正向及回滚等既有 `published()` 调用自动使用同一要求。双关时不增加 socket 要求或等待；不重构原 TPROXY/DNS 就绪策略。

## 回归设计

- `tests/unit/xray_ready.uc`：生产渲染的双关、仅 HTTP、双开、仅 SOCKS 各自产生正确要求；错误协议、非 loopback、非法端口、重复标签 fail closed。
- `tests/xray-ready/run.py`：真实 Linux socket 的本代精确 loopback 成功；本代 IPv4/IPv6 wildcard、另一 loopback 地址和其他进程持有的监听均不能代替显式入站；拒绝后占用者仍存活且其监听仍可独立通过所有权检查。这些是 socket helper 证据，不冒称 Xray 数据面。
- `tests/explicit-proxy/reload.py`：复用 `tests/reload/dns-ready.py` 的私有 sysroot/生产 daemon harness，生产 UCI、配置读取、渲染、监督、HUP reload、状态/事件发布和回滚保持真实；Xray 使用真实 ELF 引擎和完整生产配置，不移除透明/DNS 入站、不手工改写待测配置。上游为本机真实 Xray SOCKS，目标为本机 HTTP 服务，无公网依赖。
- 宿主隔离边界：nft、ip、ChinaDNS、dnsmasq、健康探测使用已有私有夹具，绝不操作宿主防火墙、路由或设备。仅在隔离复制的模块中，将 Xray `published()` 等待的**观察上下文**切为 native `/proc`/socket_diag（仍从私有 current 读取生产 artifacts）；这是为真实 Xray 的 IPv6 dual-stack TPROXY 提供原生内核证据，避免 rooted 模式刻意拒绝借用宿主双栈探测。未替换 requirements、socket 所有权判定、就绪返回值或超时。

## 实际 Xray 事务证据

已用最低支持引擎 Xray **26.3.27 / d2758a0 / go1.26.1 linux/amd64** 和 Xray **26.11.9 / 676eaf6 / go1.27.3 linux/amd64** 完成：

1. 真实 daemon 启动双关；逐次 HUP 重载 **双关 → 仅 HTTP → 两者 → 仅 SOCKS → 双关**。每次检查新的 daemon 直属真实 Xray PID、该进程 `/proc/<pid>/fd` 所有的 TCP LISTEN、启用端口只有 `127.0.0.1`；关闭端口既无本代监听，也不能建立 TCP 连接。
2. 每个启用入口均以正确账号经本机真实 Xray 上游访问 HTTP 目标成功，未认证请求失败；不只检查配置或 TCP connect。
3. 两个反例分别为 **HTTP 工作 → 外部进程占住新增 SOCKS**、**SOCKS 工作 → 外部进程占住新增 HTTP**。正式 Xray 预检查通过，但运行时 bind 失败；实际 reload 的 `last_reload.ok=false`、具有失败明细及 `START_FAILED`，无新增 `RELOAD_APPLIED`，服务保持 running。
4. 回滚后 `current/xray.json` 字节及 `render_hash` 恢复旧值，旧入口由回滚代 Xray 持有且真实认证请求再次成功。外部占用者 PID 与 socket inode 集合前后不变，仍持有原端口；未被误杀或冒认为本代 Xray。
5. 检查 daemon stdout/stderr、命令记录、运行日志、事件及 state 不含随机账号密码；不输出原始配置或含密子进程输出，临时目录及进程退出清理。

同一引擎还运行既有 `acceptance.py` 五种配置验收，覆盖真实 SOCKS/HTTP 认证、HTTP/TLS 目标、上游故障无直连回退；`diagnostics.py` 八项脱敏回归均通过。

## 确定性屏障与故障夹具证据

屏障测试与上节原生观察的真实 Xray 验收分开：在隔离模块的 socket table 读取边界隐藏显式端口行，追踪实际 gate 的 not-ready 评估。先以**另一个不隐藏 socket 行的原生观察器**读取同一份已发布 artifacts，执行未修改的生产 gate，确认本代全部非显式要求（TPROXY/被引用 DNS，而不只是进程存在或一个基础端口）已满足；记录此时 trace 索引，只统计之后三次带显式要求的 not-ready 评估，检查仍是同一 Xray PID 且没有成功发布，再主动释放屏障。轮询有总超时，但不以固定睡眠时长作为未提前发布的证据。引擎本身仍为真实 Xray；**隐藏后的 socket 视图是故障夹具，不是引擎未 bind 的证明**。另在隔离模块删除新增的显式 requirements，要求屏障能捕获基线的提前成功，证明回归具有缺陷敏感性。

Xray 26.3.27 和 26.11.9 下，首次启动仅 HTTP、重载 HTTP→双开均在屏障内观察到至少三次具有显式要求的 not-ready 评估；首次启动未发布 running/`SERVICE_STARTED`，重载未发布 `RELOAD_APPLIED` 且 `last_reload` 保持旧值。主动释放后才成功，随后实际认证请求通过。隔离删除显式 requirements 的负控从双关启动，再新增 HTTP 重载，捕获到屏障未释放即 `RELOAD_APPLIED`，以预期断言失败确认缺陷敏感性；不是其他配置/引擎故障导致的失败。
