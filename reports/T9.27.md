## apply.uc 的授权改动与理由

原 sets_export 在 nft 命令失败后，除 sys.run 的 CMD_FAILED 外，还自行调用 failed() 记录 START_FAILED；仅修改 shutdown 不能消除后者。因此先停止工作并请求扩大允许范围，再按用户明确授权实现：

1. 签名变为 `sets_export(ctx, opts)`；`opts?.on_stop` 为真时，命令失败或输出解码失败仅返回 `{ ok: false, detail }`，不调用 failed()，不添加 START_FAILED。执行 nft 的 sys.run 保持原样，命令非零退出的 CMD_FAILED 也保持原样。
2. shutdown 与 apply_cleanup 两个停止场景调用点传 `{ on_stop: true }`；表是否存在仍在调用方判断，未挪入 sets_export。
3. reload.uc、monitor.uc 调用不变。不传参数时，命令失败和解码失败仍按原实现记录 START_FAILED。
4. 新测试通过真实 daemon 的 SIGHUP 重载、Xray 监听消失两轮后的 failsafe 恢复，分别触发 reload 与 monitor 的导出失败，确认 CMD_FAILED 与 START_FAILED 仍存在；另测 reload 的成功命令/非法输出仍记录 START_FAILED。
